# Issue 分诊

目的：让维护者知道**问题是什么、证据到哪一步、下一步在等谁**，不是自动确认 Bug、关单或接受需求。

## 核验

1. 阅读正文、完整评论和已有维护者决定。以该仓库默认分支的可信 SHA 为代码基线，不只看标题或其他 AI 结论。
2. 归纳用户场景、期望与实际行为。区分报告者描述、代码核验、已执行复现和未验证推测；不把用户宣称的根因直接写成已确认事实。
3. 按问题需要检查信息：codexhost / Codex Desktop 版本、OS/架构、安装方式、Harness 名称与版本、本地/SSH/Remote Control、复现、脱敏错误或截图。只问影响定位的信息；需求/文档问题不机械索要全部环境字段。
4. 在仓库已有能力、Issue、PR 和相关文档中定向查找关联。搜索结果继续分页或收窄范围，有限搜索说明边界，不声称查遍全库。
5. 关联与重复分开：同一 Harness、相近标题、同一错误字符串并不能证明相同根因。关联条目提供已核验链接及理由；不同版本、入口、失败层次或故障特征明确注明。

## 产出

按 report-format 的 Issue 结构填写：

- `title` / `originalTitle`：中文问题标题与原始标题。
- `summary`：简短描述实际问题及重要限制。
- `category`：bug / feature / question / documentation / unknown；这是本地建议，不修改标签。
- `priority`：urgent / normal / unknown。紧急建议必须在 reason 中给出影响和证据，如阻断启动、旧会话恢复或安全边界；不因措辞强烈就升级。
- `reason` 与 `evidence`：最重要的依据及验证边界。只有报告者证据时明确“据报告、尚未复现”。
- `missingInfo`：需要补充的具体信息，无缺口时为空数组。
- `related`：关联 Issue/PR URL 与关系理由，不直接判为可自动关闭的重复项。
- `action` / `nextActor`：一个明确下一步和责任方，例如作者补复现、维护者核验、贡献者补测试或维护者做产品取舍。不是自动分派任务。
- `replyDraft`：面向作者的简短回复草稿，感谢信息、说清当前判断/疑问/下一步，不承诺尚未决定的修复或发布时间。

不使用 PR 的 ACCEPT / SIMPLIFY / DISCUSS / DECLINE。请求包含多个不同问题时建议拆分，但不因为格式、篇幅或缺少模板就否定内容；不得索要 Token、完整账号文件或未脱敏日志。

停止条件：已有材料足以给出可执行下一步，或进一步判断依赖作者补充/维护者取舍。完成“请作者补哪些信息”的分诊可记为已处理来源；API/代码采集失败、分析未完成不能记完成。

发布回复、改标签、关闭或重开均不在本 skill 范围内。关闭建议必须有明确依据，例如重复关系、修复 commit/PR 与版本，或维护者不采纳理由；只提供建议供人确认。
