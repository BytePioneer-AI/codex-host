# PR 功能价值与合入建议

只回答：**这个 PR 值不值得进仓库？为了解决这个问题，代码是不是改得太多了？**这是原有 PR 评估内核，不是“技术上可以 merge”的认证。

## 评估边界

- CI 和冲突是辅助信息，用于提示修复成本和后续动作，不是硬阻断。红灯、冲突、进行中或状态未知均不能单独触发降档或延后建议。若进一步核验发现具体设计或维护问题，按该问题的证据评估；绿灯也不能证明功能有价值或实现克制。
- 路径用于找到责任归属和关键实现，不按 HIGH/MEDIUM/LOW 自动裁决。核心包可以值得合入，纯文档也可能重复或无益。
- 不按作者身份、行数或文件数判断价值。必要的跨包改动不等于过度；几十行引入多余机制也可能过度。
- 阅读关键实现和已有替代方案，不逐行挑风格、命名或格式。逐行正确性审查交给 `/review`；修 CI、处理评论交给 `/pr-babysit`，本 skill 不自动启动它们。
- 缺少需求说明不等于功能无意义；先从实现和现有文档找依据。

## 1. 核验完整文件清单和版本

选取材料已包含 PR 来源、BASE/HEAD、正文和讨论。仍需取得实际变更范围（只为本批选中 PR 执行）：

```bash
gh pr view <N> -R <OWNER/REPO> \
  --json number,title,url,state,isDraft,body,baseRefName,baseRefOid,headRefOid,changedFiles,additions,deletions
gh api --method GET --paginate --slurp 'repos/<OWNER/REPO>/pulls/<N>/files' \
  -f per_page=100 \
  --jq '[.[][] | {filename,previous_filename,status,additions,deletions}]'
```

另取辅助状态；失败记为未知，不影响核心材料完成判断：

```bash
gh pr view <N> -R <OWNER/REPO> --json statusCheckRollup,mergeable
```

记录 CI 的通过、失败（含超时等失败终态）、进行中、取消/跳过、无检查或未知状态，以及冲突的有/无/未知；混合结果保留说明。没有检查不能记为全绿，`mergeable` 未知不能猜成有冲突。只取当前快照，不等待、重跑 CI 或解决冲突。

- 核对文件清单数量与 `changedFiles`；达到 API 上限、请求失败或输出截断时补采。无法补齐则 DISCUSS，写清证据缺口并设置 `source: null`，下次重试。
- 文件清单保留测试、文档、lockfile、生成文件、重命名和删除项。可以不展开生成内容，但要确认它来自什么源变更；不能从范围判断中直接忽略。
- BASE/HEAD 与 selection 不一致时重新准备该编号的批次，不混用版本。分析后发布入口还会复核完整来源；持续变化则保留未完成说明。

完成条件：有元数据、完整文件清单与一致快照，或明确记录核心缺口。CI 未知不等于核心缺口。

## 2. 定向阅读：价值、克制、维护代价

先用标题、正文和文件清单提出一句话目标，再核验关键 diff、调用点、相关测试和基线已有能力。可用 `gh pr diff <N> -R <OWNER/REPO>` 获取 diff，只展开影响合入建议的部分；上下文不足时读取对应 base/head 版本文件。

先写清维护者卡片，再整理技术详情：

| 字段 | 要回答的问题 |
| --- | --- |
| `title` / `originalTitle` | 简洁中文功能标题；原样保存 GitHub 标题 |
| `effect` | 用户现在能做什么，或修好了什么？1–2 句，必要时补重要限制 |
| `value` | 为什么值得进仓库？1 句，不重复作用 |
| `reason` | 为什么合入、精简、讨论或拒绝？最影响决定的 1–2 点 |
| `action` | 下一步做什么？1 句 |

这六个卡片字段均为单行。技术符号、路径、测试数量、未复跑说明通常放 `scope`、`cost`、`integration` 或 `evidence`；直接决定取舍时才进入卡片。精简表达不等于减少核验深度。

每个 PR 回答以下三个问题，结论附具体代码或需求证据：

| 维度 | 核验内容 |
| --- | --- |
| 功能价值 | 谁在什么场景遇到什么问题？带来什么收益？与产品定位一致吗？已有功能或配置是否满足，PR 是否有增量收益？文档、测试、维护型 PR 同样看实际收益。 |
| 实现克制 | 主要改动是否服务目标？是否有无关重构、重复实现、过早抽象、为假想调用者增加的扩展点？是否复用了语义和所有权都适合的实现？ |
| 维护代价 | 新增哪些配置、状态、依赖、持久化、入口或兼容分支？收益是否值得长期负担？是否有保留收益、明显更小的方案？ |

具体核验：

1. 找主要行为入口、关键实现及调用者；检查相关测试是否体现目标收益，不只信 PR 描述。
2. 在基线检索最相关的既有实现。“重复”必须给出对应位置，不能仅因名称相似建议复用。
3. 对新增机制说明“解决哪个当前需求”。单一调用者是核验信号，不自动判过度；隔离平台差异或守住边界可能有充分理由。
4. 建议删减时明确删除、复用或拆出哪些机制，并解释如何保留行为、测试和边界；少写行数不能破坏这些约束。
5. 维护代价大于收益必须有具体代价和替代方向；缺少证据时提问，不把个人偏好当事实。
6. CI 失败或冲突仅在可能影响设计/维护判断时定向查日志；区分一次性修复与长期负担，不展开成 CI 调试流程。

停止条件：证据足以区分下面四档，或剩余产品取舍必须由维护者回答。不为凑问题继续展开无关代码，不把不确定性包装成“不值得做”。

## 3. 四档建议

每个非跳过 PR 恰好一档，以下顺序优先匹配。旧 FAST-MERGE 等 token 不再使用。

| Token | 看板列名 | 判定 |
| --- | --- | --- |
| DISCUSS | 需要讨论 | 足以改变结论的证据缺口、需求不明确或产品取舍。列出需要谁回答的具体问题，不能只写“人看看”。 |
| DECLINE | 不建议合入 | 有证据表明偏离方向、重复且无增量收益，或必要维护代价明显大于收益；不是因冲突、CI 或改动量大而拒绝。 |
| SIMPLIFY | 精简后合入 | 目标值得做，但有可定位、可去除的多余机制或无关改动；说明精简办法与必须保留的收益。 |
| ACCEPT | 建议合入 | 有实际收益，关键改动与目标匹配，维护代价合理，未发现需要先精简或讨论的事项；不承诺实现完全正确。 |

信息足够时不要因涉及核心包就退到 DISCUSS。能通过明确精简保留目标时用 SIMPLIFY，不因当前方案臃肿直接否定功能。

校准：真实 Thread 生命周期修复，即使跨核心包，必要且代价合理也可 ACCEPT；单个需求引入多余注册中心/持久化，可用既有路径解决则 SIMPLIFY；查阅后仍看不出场景则 DISCUSS；核验为已有能力且无收益则 DECLINE，即使只改几十行。文档、测试和 CI 配置也必须说明实际维护收益。

完成条件：唯一档位、一行理由、三个维度的证据或明确缺口。SIMPLIFY 有可执行精简建议，DISCUSS 有具体问题；本批回复草稿、下一步负责人、是否完成来源核验均已填入报告。
