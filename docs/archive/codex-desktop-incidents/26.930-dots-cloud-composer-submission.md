# Codex Desktop 26.930 Dots 云房间 Composer 提交被拦截

本文记录 Codex Desktop `26.930.51102`（build `13100`）的 Dots（OpenAI always-on agent，Orbit 云房间）会话框在 codexhost `0.12.1` 下无法发送消息的现场结论，以及上游修复 `#486` / `#490` 在 macOS 上的实测结果。识别依赖 Desktop 私有的 `isOrbit` React prop，更新 Desktop 后应重新做现场探针。

## 现场环境

- Codex Desktop：`26.930.51102` / build `13100`，Chromium `154.0.8037.98`
- codexhost：`0.12.1`（macOS 安装版，本地 Host）
- Dots 房间入口名 "Roy"，`roomId=d5ad4dd7fb4081a3bb2584728fa1307e`
- 日志：`~/Library/Logs/com.openai.codex/2026/10/07/`

## 用户现象

- 经 codexhost 启动：Dots 会话框正常渲染、可以输入，但点击发送按钮或按 Enter 均无反应，也没有错误提示；普通 Codex 与外部 Harness 线程不受影响。
- 不经 codexhost 直接打开 app：同一房间发送正常。
- codexhost 会话日志里 Orbit 房间挂载正常（`stage=client.composer` → `stage=client.ready`），但全程没有任何 `stage=client.http_send` 事件——提交根本没进入 orbit messaging 层。
- 直启对照会话里发送表现为 `stage=client.http_send outcome=started` → `outcome=success`（messageId 已分配）。

## 根因

Dots 云房间的 composer 复用了 Codex composer 的 DOM 标记 `[data-codex-composer-root]` 与 `conversationId`，但没有 app-server Thread，也没有 Harness 配置。codexhost `0.12.1` 的 renderer 扩展把它当成原生/外部 composer 挂载（#486 描述原文：treated them as app-server Threads, showed an Agent ownership error (`!`), and intercepted message submission）：

- 共享的 `conversationId` 经 `findComposerModelTarget` 推出伪 `["conversation", <cloud id>]` 模型目标，该 Thread 的 ownership 检查永远失败；
- binding probe 安装在 document 捕获阶段的 `keydown` / `click` / `submit` 监听，在 ownership 被判定阻塞或 `applyComposerAgent` 失败时对该事件 `preventDefault()` + `stopImmediatePropagation()`，并直接把发送按钮置为 `disabled`。

本现场的观测是"能打字、发不出、无报错"。网络层与此无关：codexhost 会话里 Orbit 的 `host.request` / `host.network` / `host.auth` / `host.device_cookie` 阶段全部 success，房间与历史也正常拉取。

## 修复

| 提交 | 内容 |
| --- | --- |
| `a6f9d581`（#486，v0.12.2） | 新增 `isOrbitComposer`：在挂载控件、推导 Model target、应用 Harness 配置之前，沿已提交 React 树向上找最近的显式 `isOrbit` owner；ProseMirror 编辑器自身可能没有 React DOM 指针，识别必须从编辑器向上走。已识别的 Orbit composer 不再注入控件、不再拦截提交，并忽略此前 Thread 的 ownership 响应。 |
| `40ee7164`（#490） | composer 被同目标替换转移后保留 pending submission 标记，避免后续 ownership 检查失败再次阻塞提交。 |

#486 的 PR 说明注明 Windows 实测已确认恢复，但 "A Mac dot send was not tested"。

## macOS 实测（本记录补充）

在 `26.930.51102` + main 构建（`d2ee6150`，含 #486/#490）上验证同一房间：

- Dots composer 不再被挂载：composer root 上 codexhost 控件数量为 0（`data-codexhost-agent-control`、`data-codexhost-model-control`、`data-codexhost-usage-control` 等均不存在）；
- 向编辑器注入文本后，发送按钮从 `disabled` 变为可用；
- 受信点击提交后，日志出现 `stage=client.http_send outcome=started` → `outcome=success`，messageId 已分配。

即 Dots 发送在 macOS 上随 v0.12.2 恢复，补上了 #486 的 Mac 验证缺口。

## 诊断签名

| 观测点 | 0.12.1（坏） | 直启 / 修复后 |
| --- | --- | --- |
| `orbit.startup.stage` | `client.composer` / `client.ready` 正常 | 相同 |
| `orbit.messaging.stage` 的 `client.http_send` | 缺失 | 发送时出现，`outcome=success` |
| `host.request` / `host.auth` / `host.network` | 全 success（排除网络） | 相同 |
| Renderer：Dots composer root 上的 codexhost 控件 | 存在（被挂载） | 0（未挂载） |

判别顺序：先看 `client.http_send` 是否出现。缺失而 `host.*` 全 success，说明提交被 renderer 层拦截，与网络、代理、账号无关；再经 CDP 读 `window.__codexhostRendererBindingProbeV1.status()` 与 composer root 的 codexhost 控件确认挂载状态。

## 边界

- `isOrbitComposer` 依赖 Desktop 私有 `isOrbit` prop；Desktop 后续版本如改动该标记需复核（#486 已注明）。
- 分类为三态（`orbitComposerKind`：`orbit` / `codex` / `unknown`）。composer 根在 12 层祖先内没有 React 指针时仍按原生 composer 处理（云房间总会发布指针）；指针存在但已提交树走查放弃（`return` 环、无发布根、访问上限触发 `codexhost:react-fiber-walk-limit`）时按 `unknown` 处理：不再挂载控件、不派生 Model target、不接收转移状态，已挂载的根保留现有状态等下一次可分类的扫描，避免在原生 composer 上闪动。
- 事发当天早些时候的一个直启会话出现单次 `httpStatus=403` 与三次 300 秒等待回复超时，属服务端瞬态，与本事故无关。
