# Codex 原生账号切换设计

**状态：用户已授权在独立 worktree 实现，当前仍在验收，不是已发布能力。** 实现目录为 `../codex-host-native-accounts`，分支 `feat/codex-native-account-switching`，基线 `9d22515ec63d5ff79eec4a12d6d56b721b2bd361`。用户随后已授权提交、推送并创建普通审查 PR #262，并明确允许起停 Desktop 进行诊断；真实账号操作、真实系统凭据生命周期和发布仍未获授权。完整迁移及真实平台联合验收仍是发布门槛。

## 1. 方案摘要

从主分支新建实现分支，以 **opencodex 的 native profile 实现为核心参考**，择取 PR #252 经复核的底层能力、产品改动和测试；不继续在 #252 的协调架构上堆补丁，也不全部从零编写。

目标是：**一份官方会话存储、最多一个存活的官方 app-server、多份安全保存的账号凭据。空闲时停止后台、替换原生凭据、重启验证；Desktop、Host 和其他 Harness 不重启。**

本轮实施采用两个关键选择：

1. 本地托管模式统一使用官方受保护 loopback listener，避免 stdio 唯一连接被管理初始化和 Desktop 接入争用。
2. 添加／重新登录参考 opencodex 的 staging：使用短命、仅认证的临时目录；开始前停止任务后台，结束并确认登录进程退出后再启动任务后台。它不是按账号保存的运行环境，不执行用户任务。

第二项取代早期“所有登录也在共享 home 中完成”的设想。认证 staging 不能变成长驻账号 home，也不改变正式会话存储只有一份的约束。

## 2. 用户可见语义

- 切换作用于当前 Host 的全部 Codex Thread。已有 Thread 的后续 Turn 使用新账号；Thread ID、历史和 Harness 归属不变。
- 不保留 per-Thread／per-draft 账号选择，不按账号切换 Model、Provider、工作目录或权限策略。
- 有在途请求、活跃 Turn、工具／审批、后台终端、实时会话、压缩、待执行队列或可自动继续的工作时，返回 `busy`。不强制取消、不等待排队、不把用户输入偷偷延期到新账号执行。
- 切换入口只在账号设置页；Harness picker 只有一个 Codex。Composer 可只读显示当前身份。
- 添加 B 时暂停当前 Host 的 Codex 工作。若已有当前 A，成功后仍使用 A；若此前未登录，首次成功登录成为当前账号。
- 删除只允许非当前保存账号，不删除任何 Thread、共享 home 或迁移原件。当前账号需先切换，或使用受控退出登录操作。退出只取消当前运行身份，保存账号仍可再次选择；删除保存凭据是另一项明确操作。
- 提示用户：继续原 Thread 会把已有上下文用于新账号的后续请求；切换账号不是切换独立的数据空间，也不承诺实际 Billing Source 一定随账号变化。
- SSH 首期维持远端原生单账号，不传输本地凭据，不开放远程账号库管理。

## 4. Module 划分与所有权

只建立两个主要对外 Module，凭据存储与恢复是账号 Module 的内部实现，不再保留 Pool 形状的转发层。

```text
Desktop / 设置页 / Host 内部委派
                 │
           AppServerHost
          ┌──────┴────────┐
     账号管理请求       官方工作请求
          │               │
    CodexAccounts ─── OfficialRuntime ─── 唯一官方 app-server
          │               │
   加密 Vault / Journal    准入、连接代次、原生订阅恢复
          └──────┬────────┘
         Rust 通用平台原语
      私有文件 / OS 密钥 / 进程监督
```

### CodexAccounts

Interface 面向业务操作：读取快照、切换、开始／取消登录、删除、受控退出、重试恢复。调用方不传凭据、不控制 journal 阶段、不自行保存源快照。

它唯一拥有账号事务、登录操作归属和恢复决策。设置页添加与原生 Desktop 登录共用同一 staging／事务，但后者保留“登录后使用该身份”的原生语义；此激活意图必须持久保存。原生入口返回启动响应及完成 Promise，保留早到结果而不另建登录状态机。`ManagedNativeAuth` 只处理协议投递和正式后台代次通知，不拥有凭据或进程。内部包含 Vault 编解码／持久化、原生凭据识别、纯恢复决策。**不再由登录控制器和切换器分别实现一套旧凭据回滚。** 不引入通用工作流框架。

### OfficialRuntime

Interface 面向一个官方运行实例：接入客户端、发送原生请求、取得独占变更租约、停止并证明退出、启动管理或任务连接、验证与恢复订阅。

它拥有所有官方工作准入和连接代次，无法绕过它另启账号后台。账号 Module 在独占租约内操作；普通 Desktop 和委派请求走同一个准入入口。其内部请求关联继续复用现有 Broker，不另发明 RPC 协议。

### 归属约束

- `host-runtime`：账号语义、加密格式、恢复决策、官方协议与组成。
- `crates/platform`／`launcher`：通用私有文件、系统密钥存取、进程身份与监督；不认识 Account、OAuth 或 Thread。
- `shared-contracts`：仅浏览器安全的公开状态和错误；不依赖其他 Workspace 包。
- `renderer-extension`：显示、确认、提交操作和处理状态修订；不接触 Token、文件路径或原生私有连接。
- 非当前额度和旧布局迁移分别为独立职责，不进入每个 Codex 工作请求的正常路径。

## 5. 存储与安全模型

### 5.1 一份会话存储，一个账号 Vault

正式 `CODEX_HOME` 由启动配置解析并规范化后固定，切换不改变该路径。官方 Thread、配置、历史、项目状态仍由官方 Codex 维护。

参考 opencodex，将账号目录、已提交 current 引用和非当前加密凭据合在一个原子持久化的 Vault 中，**不再分别提交 accounts.json 指针和独立凭据槽来表达一次成功**。Vault 包含版本、home 标识、revision、本地账号 ID、身份关联、展示信息和加密 payload。

- 当前账号的凭据权威是正式 home 的原生存储；Vault 不把旧登录快照当作其最新版本。
- 非当前账号的权威是 Vault 中的加密凭据。
- 事务中的源／目标备份也加密。保留原生文档未知字段和完整字节，不重建一个“等价”auth.json。
- 身份关联采用 issuer＋稳定用户标识＋workspace；不能仅凭邮箱或 workspace 去重。JWT 解码只用于关联，不能代替认证验证。
- staging 仅保存一次登录的短命认证状态，不保存用户 Thread，也不成为账号的长期 home。

Vault、Journal、staging 注册记录和运行见证关联同一个规范化 home，并使用与 opencodex 分离的存储／密钥命名空间。不得复用或修改用户的 opencodex Vault。

### 5.2 加密、权限与写入

- 非当前凭据采用 AES-256-GCM，随机 nonce；关联数据绑定格式版本、home、本地账号 ID、身份关联和文档摘要，参考 opencodex 防止密文被移装。
- 每个托管 home 的随机密钥由系统凭据存储管理。已有 Vault 丢失密钥时不创建新密钥冒充恢复，不退回明文。
- 主 auth.json 和登录 staging 中的 auth.json 是官方文件认证所需的明文例外，必须严格限制权限、存活范围和访问方。
- 私有文件 helper 在同一进程中持锁并串行执行后续 I/O；只读目录 facade 共享租约、64 项有界队列和 fail-closed 状态。操作前后核对租约路径身份；Windows 校验 DACL，macOS 保守拒绝非空扩展 ACL。不能把正常并发误报为 writer 故障，也不能在未确认 writer 退出时释放独立的锁 helper。
- 容量预算在写前预检：单凭据 256 KiB，Vault 4 MiB，Journal 17 MiB，通用私有文件 20 MiB，IPC frame 为文件预算四倍加 16 KiB。最多 128 个账号，同时受实际字节预算限制。
- 日志、Renderer、普通元数据响应、命令行参数均不得携带凭据或完整认证文件。错误只返回稳定类别和安全提示。
- 清理不宣称能在 SSD／文件系统快照上物理擦除秘密；目标是避免长期明文副本、限制权限，并准确报告未完成清理。

独占托管是切换前提。Host 的锁约束受控写入者，但不能宣称它能阻止任意外部 Codex CLI 或同用户程序写 auth.json；无法确认其他写入者已停止时拒绝切换，发现第三方身份或摘要冲突时不覆盖。不会为了取得所有权自动杀死不属于 Host 的进程。

## 6. 单后台与冷启动

### 6.1 推荐统一本地官方 listener

macOS、Windows、本地 Linux 的托管模式均使用官方 app-server 的受保护 loopback listener：绑定回环地址和动态端口，启用官方 capability-token 认证。令牌仅在 Host 内存中，命令行仅携带官方要求的摘要，Renderer 不直接连接该 listener。

同一个进程提供一个 Host 专用管理连接和各 Desktop 的独立原生客户端连接。**多个连接不是多个后台。** Desktop→Host 的现有传输保持不变；这也不是模型请求代理，模型连接仍由原生 Codex 自己建立。

这样消除 #252 中“先等待账号初始化完成，再创建唯一可完成初始化的 Desktop 客户端”的循环依赖。若某版本不支持所需私有 listener／原生能力，只禁用托管切换，不用无保护监听器替代。

### 6.2 冷启动顺序

1. 接通 Host／外部 Harness 所需控制面；官方工作准入保持关闭。账号初始化失败不能触发 Host 全局清理。活着的 Host 在 Codex unavailable/changing 时仍以自身元数据应答 Desktop initialize，保留原生协商参数；不连接 staging、不虚报认证，恢复后沿用同一连接。
2. 解析 home，确认托管所有权和旧进程树状态；检查 Journal、Vault、staging 和迁移记录。**先处理恢复，不能先自动导入 auth.json 或修改 current。** 若精确摘要证明目标已安装但阶段未推进，先补全该事实记录；事实不明时不启动可能刷新凭据的后台。
3. 如实际生效配置必须经官方协议读取，只允许以唯一后台、管理连接、用户 Thread 不恢复的方式探测。仅对已验证不会自行执行工作的平台／版本启用；需要写凭据前再次停止并确认退出。
4. 依据实际凭据、提交事实和记录完成恢复；无未决记录时才处理首次导入。
5. 启动正式后台，先初始化管理连接，再初始化 Desktop 连接并验证原生身份。首次导入只能在确认身份后提交。
6. 开放官方工作，发布一次确认后的状态；不会给 Desktop 重发已有会话的 initialize 响应。

### 6.3 不支持管理不等于不能使用原生 Codex

- 没有未决事务、没有身份／所有权冲突，仅因存储、OS 密钥能力或版本不受支持：保留安全的原生单账号运行，管理能力为 false；不改配置、不导出 keyring 凭据、不启动额外后台。
- 有未决事务、未知写入者、无法读取关键恢复事实：只有 Codex 进入 unavailable，保留其他 Harness。已建立的账号管理器提供受控 recover；初始化所有权都无法建立的静态 unavailable 不谎报可原地重试，需要先处理冲突后重新初始化 Host。
- 不托管时的真实身份由原生 account/read 展示，不拿旧 Vault current 冒充实际身份。重新启用管理前重新核对，不静默收编外部登录。
- 支持范围由平台＋官方版本／能力＋执行证据定义。不能把当前已研究过的 `0.153.4` 当成所有平台都已通过，也不把版本白名单误用为所有原生请求的开关。

## 7. 切换事务：以 opencodex 的模型为主线

### 7.1 不变量

1. 任何时刻最多一个存活的官方 app-server，包括临时登录用途。
2. Host 只在确认相应原生写入者退出后安装／删除原生凭据。
3. 切换提交前不接收新官方工作；不自动重放产生副作用的请求。
4. 身份相同但摘要更新时，实际原生文件优先于旧快照；不能通过回滚倒退 Token。
5. 凭据事务提交和清理是两件事。提交后清理失败不能反向解释为“尚未提交”。
6. 未知身份、丢失密钥、无退出证明都不能通过猜测或覆盖文件解决。

### 7.2 A → B 正常流程

```text
取得独占变更租约，关闭新工作准入
    → 检查在途工作、原生活动和 Thread 可恢复性；忙则原样拒绝
    → 完成存储／密钥预检，解密并核对 B；失败不停止正常运行的 A
    → 停止 A 并确认整个受控进程树退出
    → 读取实际最新 A，核对来源身份
    → 持久化 prepared Journal，含加密源／目标和 before/after Vault
    → 原子安装 B，读回校验；记录 auth-replaced
    → 启动唯一 B 后台，仅初始化管理／协议，不恢复用户工作
    → 原生 account/read＋受认证轻量读取确认 B 可用
    → 原子提交 Vault：current=B，A 的最新凭据成为非当前 payload
    → 记录 vault-committed，完成连接准备与清理
    → 开放工作，广播 B 的确认状态
```

保留 opencodex 的三个主要持久阶段 `prepared / auth-replaced / vault-committed`。Vault 同时保存 `lastOperationId` 作为提交收据，补偿前在 Journal 中持久保存最新目标及 rollback 意图。明确适配点是：**原生后台认证检查插在 Vault 提交前**，而不是将 opencodex 的离线文件替换成功直接当作 Desktop 已可继续工作。

官方认证检查使用支持版本的真实认证接口，不发起 Model Turn、不以邮箱出现或模型自报身份作为成功证明。准备完成后若只是后续某个 Thread 无法恢复，报告该 Thread 的问题，不倒转已经提交的全局身份。

### 7.3 失败与恢复规则

| 观察到的事实 | 决策 |
| --- | --- |
| 尚未停止或不能证明旧进程树退出 | 不写目标、不启动竞争后台；busy 原样返回，退出不明则 unavailable |
| 实际仍为源 A，Vault 未提交目标 | 保留最新 A，不安装旧 A 快照；确认 A 可继续后结束失败操作 |
| 实际为 B，Vault 尚未提交 | 正常切换失败时先停止 B、加密保全最新 B，再恢复并验证 A；崩溃重启时按原操作意图重新验证 B 后完成提交，不能验证则按同一规则恢复 A |
| Vault 已确认提交 B，Journal 未更新或清理失败 | 以实际 B 和已提交 Vault 收尾，不因旧 Journal 阶段回退 A；不能安全收尾则保留 B 为已提交状态并关闭准入 |
| 第三方身份、摘要不可解释、Vault 与 Journal 不匹配 | 不覆盖；保留私有证据，进入恢复处理 |
| 源／目标同一身份，例如当前账号重登 | 用原子安装事实、字节摘要及凭据修订区分版本，不能按账号 ID 当作幂等，也不能按身份相同恢复旧 Token |

恢复决策采用 opencodex 的“观察事实 → 纯决策 → 唯一执行者”结构，但不能机械照搬其只处理两个不同已保存身份的类型。未登录、同身份重登以及提交确认丢失必须有明确测试。

任何可能刷新目标 Token 的后台启动前，必须先持久化 `auth-replaced`；安装完成但阶段写入失败时，用 Journal 中源／目标的精确摘要和真实提交内容判定。若这些事实仍不能解释文件变化，就保留实际文件并要求恢复，不能杜撰一个“更新的凭据版本”。

`recover` 是可重试的受控操作。它不能删除 Journal 来假装恢复，也不接受 Renderer 提供的凭据或文件路径；未知身份需要用户先处理实际冲突，再重试。因一次可重试认证故障而失败，不应要求退出其他 Harness。

## 8. 登录：推荐采用 opencodex 的隔离 staging

### 8.1 添加 B，当前为 A

```text
取得同一独占租约，确认空闲并停止任务后台
    → 创建私有、可追踪的一次性登录目录
    → 在该目录启动唯一官方登录后台，只允许认证／验证操作
    → 发起原生设备代码登录，向 UI 返回 operationId、链接和设备代码
    → 匹配本次原生完成事件并验证用户＋workspace
    → 停止登录进程树，读取最后落盘的凭据并核对身份
    → 原子提交 Vault 中 B 的加密凭据
    → 清理 staging，重启原正式 home 的 A
```

**A 的 auth.json 从未被新登录覆盖，因此添加 B 不需要恢复一份旧 A 快照。** 这比 #252 的“清空 A → 登录 B → 再写回 A”减少一个高风险往返，也是本方案真正借鉴 opencodex 的关键处。

staging 初始化不继承正式 home 的用户任务、插件或自动继续状态；使用显式的最小认证配置，不改变正式 home 配置。不能在 staging 中创建用户 Thread 或发起推理。

### 8.2 首次登录、重登、取消和故障

- 无当前账号：取得 B 后通过同一凭据切换事务安装到正式 home、验证并提交 current；登录暂存不直接抢先改 current。
- 非当前账号重登：验证必须匹配所请求的用户＋workspace，更新该账号加密 payload，不改变当前身份。
- 当前账号重登：staging 验证新授权后，通过同一原生安装事务替换当前凭据；不能命中“选了同一账号，无事可做”的幂等分支。新授权已安装／发生轮换时不自动降级旧授权。
- 取消／超时：先终结本次登录进程树，再清理 staging、恢复正式后台。迟到事件按 operationId 和进程代次丢弃；它的写入只能落在该次 staging，不能改正式 auth.json。
- B 已保存而 staging 清理失败／A 重启失败：如实显示“B 已保存，清理或 Codex 恢复待完成”，不能删除 B 或重复导入来伪装整个操作未发生。
- 崩溃：启动时先按 staging 归属、退出事实、是否已提交处理；没有确认登录完成的残留不自动计为已连接账号。清理失败不忽略、不自动启动新的并行登录。
- Desktop 直接发起 ChatGPT OAuth／设备代码登录、取消、退出时，托管模式统一进入账号 Module。原生登录激活目标身份，设置页添加则可只保存；staging 记录 `activateOnSuccess`，避免崩溃后丢失激活意图。支持的 branding／streamlined 参数原样传入原生后台。
- 原生 `account/login/completed` 在对应启动应答写出后投递，保留操作 ID 和支持的 onboarding 字段；正式后台未就绪不能报告原生登录成功。取消返回原生 `status: canceled/notFound`，不套用设置页的 `cancelled` 布尔响应。
- 正式后台的新 generation 确认 ready 后，从它的 `account/read(refreshToken:false)` 取得真实模式／套餐并投递 `account/updated`；staging 和退休代次不能冒充当前身份。通知读取不获取凭据变更租约，慢客户端或观察者失败不回滚提交。
- 不支持的原生登录类型在任何改写前拒绝。不托管且无未决事务时仍保留官方自身认证语义。

受控退出登录使用同一原生凭据事务，目标为“无凭据”：空闲后停止、加密保存当前最新凭据、移除正式 auth.json、启动并确认原生已退出，最后提交 current=null。明确记录这一操作意图，不能把恢复期间任意缺失的 auth.json 都解释为正常退出。

staging 的租约／清理记录保持独立职责，不把它膨胀成通用 Job 系统。共享 home 的切换仍只有一个 Journal 和一个事务所有者。

## 9. 工作准入、Thread 连续性与公开状态

### 9.1 工作准入与重连

- 普通请求取得工作租约；长期原生活动由原生开始／终态及只读核对共同确认，不能只数 RPC 响应。
- 工作类别覆盖 #252 已盘点的 Turn、process、shell、审批、realtime、compact、queue、goal 等。关闭客户端不等于工作结束；剩余客户端收到同一原生活动的终态后也能正确结算，不能留下永久 busy 标记。
- 已确认能跨重启恢复的 Thread，才允许参与切换。不可恢复的临时状态明确拒绝，不偷偷改名促成持久化、不新建 Thread 假装原 ID 连续。官方 `0.153.4` 可能在 rollout 尚未物化时先返回计划路径；原生 resume 报告无 rollout 时按 `busy` 保留内存 Thread，不能误报登录失败。
- 每个新官方进程有新 generation。旧响应、通知、审批回复和缓存结果不能进入新代次。Owner 在每次真实后台停止后通知仍附着的客户端清理旧工作记账；不能依赖一次性 startup failure，或把 EOF／客户端关闭当成退出证明。
- 保存最少必要的原生初始化／订阅信息；切换前用原生事实核对实际 Model、Provider、推理强度及恢复设置，不用最初 draft 参数覆盖后续选择。
- 成功后按原 ID 懒恢复，调用官方 resume／订阅机制；不复制历史，不重放 Turn，不自动执行积压输入。

### 9.2 公开 Interface

账号快照使用一个清晰的 v2 契约，包含：当前 Host 的状态修订、`ready/changing/unavailable`、管理能力及原因、已提交 current 引用、可展示账号列表，以及必要的当前操作／清理提示。

对外操作为 `list`、`switch`、`login/start`、`login/cancel`、`delete`、受控 `logout` 和 `recover`；复用现有 `codexhost/account/*` 命名空间，不保留旧 `activate` 作为语义不明的别名。旧 draft 账号参数明确拒绝。

- `busy` 是操作拒绝原因，不新增一个持久账号状态。
- `currentAccountId` 只表示 Vault 的已提交身份；phase 不为 ready 时不能据它宣称实际后台已可用。未托管身份由原生接口表示，不能把缺少库中 ID 擅自解释为已退出登录。
- UI 按 Host 会话标识＋单调 revision 接收更新，避免 Host 重启或快速切换后接纳旧结果。
- 清理失败与业务提交结果分开表达；稳定错误包括 busy、changing、unsupported、authentication-failed、stop-unconfirmed、recovery-required，不透出底层秘密。

## 10. 额度与迁移：保留目标，独立交付

### 10.1 账号额度

完整目标保留当前和非当前账号额度，不为查询额度启动官方任务后台或隐式切换。

- 当前账号通过唯一官方后台读取，其 Token 刷新仍归原生 Codex。
- 非当前账号参考 opencodex 直接 WHAM 查询；凭据只在 Host 内解密，额度快照单独持久化且不含秘密。失败保留 last-good，显示获取时间，不补零。
- 普通网络读取可有界并发，存储 I/O 由其实际 Interface 调度。
- 非当前 OAuth 刷新若启用，必须通过账号 Module 取得凭据修改租约：每账号 single-flight、凭据摘要／revision CAS、用户＋workspace 复核。整个刷新和安全写回期间阻止它被激活，不能把一次读取许可误当成永久刷新所有权。
- Vault 的并发提交在账号 Module 内合并当前状态，只修改目标账号；不能拿旧全库快照换个 CAS 摘要后覆盖其他账号。
- 只允许当前账号消费重置卡；不自动重试消费请求。Thread 累计用量与账号额度分离。

这部分作为独立职责和聚焦测试验证。本轮已在同一实现 worktree 接入非当前读取和 OAuth 刷新，没有因模块拆分取消已有能力，也没有创建发布 PR。

### 10.2 旧多 home 迁移

迁移是正式替代旧实现的交付门槛，不是启动时顺手复制文件。本文只定义技术约束，**不生成迁移操作向导**；用户交互阶段及采集值另行审查。

- 新安装／无旧多 home：直接采用现有正式 home，先检查恢复记录，再确认原生身份并登记。
- 有旧布局：独立盘点 home、凭据、会话、归档、配置、项目关系、附件、记忆、队列／目标和数据库 schema；只读报告不输出秘密。
- 保留已有正式 home 为目标，不因旧 active 指向某账号就改变会话目录。旧 active 的选择意图在凭据导入、历史验证完成后单独兑现。
- 必须确认所有旧官方写入者退出；“launcher PID 存在”不能替代退出证明。写入前形成一致性备份并取得用户确认，源目录不自动删除。
- 只迁移已验证能完整保留的布局。不能只复制 rollout 后忽略 DB、附件和关系；未知 schema 或冲突应阻断切换到新布局，不启动旧多后台 fallback 来掩盖问题。
- 同 ID 同内容可幂等，冲突不覆盖。验证需包含原生 list／read／resume、内容和关联数据，而不仅是文件数量。
- 迁移完成才提交新布局；旧 Thread→Account 文件只作为只读迁移输入，不再参与执行路由。新布局有新工作后禁止整体旧 home 回滚。
- 对尚不支持的旧布局，保留原安装和数据并明确提示不能升级；不能展示“迁移成功”却让部分历史消失。新运行中若发现未决迁移，仅限制 Codex，其他 Harness 不关闭。

## 11. 如何控制代码与验证规模

以下是可独立审查的职责分层，不表示已拆成多个 PR。本轮在同一独立 worktree 和审查 PR #262 实现，以分层测试验证；拆分不减少必要安全检查：

1. **基础验证 PR**：固定 opencodex 来源和关键行为测试，移植／完善通用私有文件、OS 密钥、进程监督；验证本地单 listener＋管理连接冷启动。不修改用户凭据。
2. **核心纵向 PR**：Vault、切换／恢复、隔离登录、原 Thread 连续性和最小全局 UI。以公共 Interface 做组合故障测试，不靠互相过度放宽的 mock 拼出成功。
3. **额度 PR**：非当前读取／受控刷新、并发持久化及多窗口展示。
4. **迁移与发布 PR**：支持矩阵、数据保全、旧路由完整删除、真实平台／Desktop 验收和文档对账。

中间 PR 可依赖或堆叠审查，不发布会破坏现有行为的半成品；正式生效时不保留两套可执行账号路由。迁移和必要原生验证未完成前，不宣称可以替代旧版本。

必须通过的行为验收：

- 从空数据和已有登录冷启动，Desktop 尚未 attach 时管理初始化仍可完成；管理连接与 Desktop 连接不争用 stdio。
- 同一 Thread 完成 A→B→A，账号来自真实请求认证证据，不靠模型自报；累计历史、Model／Provider 和权限设置保持。
- 在每个持久写入、原子安装和真实进程退出点注入失败／重启，覆盖提交确认丢失、清理失败、原生 Token 轮换、同身份重登、首次登录崩溃和未知写入者。
- 当前账号添加 B／取消 B 不改写正式 auth.json；迟到登录写入不能触及正式 home；任意时刻不并行存在任务与登录后台。
- 忙碌、审批、队列、实时、后台进程及客户端关闭竞态不会被误判为可切换；不发生请求自动重放。
- Desktop／Host PID 保持，其他 Harness 的流式输出、审批、取消和保存跨切换继续工作，失败路径也不执行 Host 全局清理。
- 真实 OS 密钥和权限测试、真实私有 I/O 并发、原生文件支持矩阵、冷启动网络失败、不支持管理但原生仍可用。
- 原 #252 审查的五类隔离复现场景在新设计中成为回归测试；另外覆盖新 staging、加密 Vault 及迁移行为。

真实账号／额度／原生刷新验证必须在获得授权后使用隔离环境。测试与性能结果分平台记录，未运行的平台不声称支持。代码量不作为验收指标，不承诺“只需几百行”；目标是只维护一套真实业务流程。

## 12. 已采用的实施决策

用户本次实现授权采用以下主线；该授权不包含真实账号操作、发布或未确认的迁移向导：

1. **全局、空闲切换**：busy 时直接拒绝；Desktop／Host 不重启；已有 Thread 后续请求使用新账号。
2. **统一本地 listener**：托管模式用官方受保护 loopback listener＋专用管理连接，Desktop→Host 传输不变。
3. **允许认证 staging**：唯一会话目录不变；允许短命登录目录，但任务与登录后台严格不并行。
4. **加密 Vault**：采用 opencodex 的系统密钥＋加密非当前凭据；没有安全能力时禁用管理，不静默退回明文，不错误禁用正常原生使用。
5. **拆分实现、不缩水交付**：额度和迁移独立验证；无法无损迁移的旧布局不自动升级，也不隐瞒历史缺失。

## 13. 当前实施与验收边界

- 已实现统一 Vault／事务／登录控制面、唯一后台与工作准入、全局 UI、非当前额度、通用密钥／文件／进程原语；删除旧账号后台池和 Thread→Account 执行路由。
- 旧布局检测只进行有界元数据校验和 home 顶层条目盘点。只有单一正式 home 原地采用；多 home、外部 home、损坏记录或孤立绑定返回 `migration-required`。它不是完整数据库迁移工具，不会宣称附件、记忆、队列、项目关系已经合并。
- 原生私有文件测试在临时目录使用合成数据和假密钥。macOS 已运行实际 helper 测试；Windows／Linux 编译检查不等于对应平台运行验证。Windows launcher 交叉构建还受 `llvm-rc` 工具缺失限制。
- 官方 `0.153.4` 的完整离线协议需要 `app-server generate-ts --experimental`。默认生成结果省略 queue／settings 等接口，不能据此误报版本缺失；生成协议也不等于真实账号验证。
- 后续已在 macOS 起停真实 Desktop，并修复 LaunchServices 路径转发和 Chromium profile 隔离；另用真实官方 CLI／compiled helper、临时 home 和假 Vault 密钥验证受保护 listener 冷启动、OAuth 开始／取消及未落盘 Thread 拒绝。没有打开授权链接、完成真实登录或执行推理；此前隔离不完整的尝试不计为隔离验收。
- 真实 OS 密钥授权／锁定行为、Desktop 同 Thread A→B→A、其他 Harness 联合运行及完整多 home 迁移尚未验收。不得将合成测试成功解释为这些项目已通过。
- 对应规格、任务与执行证据见 [OpenSpec 实施记录](../openspec/changes/implement-codex-native-accounts/tasks.md)。
