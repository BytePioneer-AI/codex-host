# codexhost 界面扩展插件方案

> 状态：分类、管理方式与第一期目标已确定；DSH Web 外置包安装、原生前后端加载、启停和恢复已实现，完整主题配置、面板与展示插件验收、原生格式和 GUI 接入仍待完成。当前行为和验证范围以 [Web 界面扩展](../product/web-ui-extensions.md)为准；下文保留完整目标，不代表第一期已全部交付。现有 Harness 插件行为以[插件运行时说明](../architecture/harness-plugin-runtime.md)为准。

codexhost 的目标是提供统一的插件管理入口，按职责区分 Harness 插件与界面扩展。界面扩展首先兼容 DSH 原生 Web 插件，并为 codexhost 原生插件和 Codex GUI 扩展保留接入边界。第一期复用已有 Cordis、客户端模块加载器、主题和 UI 插槽，逐步完成 DSH Web 插件的安装、加载、配置与禁用恢复。

本文中的 GUI 指 codexhost 在 Codex Desktop 内提供的界面扩展，不指 OpenAI 官方插件包格式。Web 与 GUI 是运行目标，插件作者可以只支持其中一端，也可以分别提供两端入口，不要求一套界面代码适配两端。

## 插件分类

按职责分为两类，按接入格式有三种。格式和运行目标分别记录。

| 职责分类 | 接入格式 | 用途与执行归属 | 实施范围 |
| --- | --- | --- | --- |
| Harness 插件 | 现有 Harness manifest 与 Adapter 工厂 | 接入 Agent Harness，由目标 CH Host 加载，原生执行语义属于对应 Adapter 和 Harness | 沿用现有实现 |
| 界面扩展 | codexhost 原生格式 | 扩展主题、页面、侧栏和展示组件，由所声明的 Web 或 GUI 宿主加载 | 预留接入，具体格式由首个原生插件确定 |
| 界面扩展 | DSH 兼容格式 | 使用原生 DSH Web 发布包，由 Web 的嵌入运行时加载服务端入口与客户端贡献 | 第一期实现 |

DSH 兼容插件保留原包和原生客户端格式，不要求作者增加 codexhost manifest。兼容模块将包信息映射为管理记录；它不把 DSH 插件转换成 Harness 插件，也不为其分配 Harness ID。

现有 Harness manifest 的 `surfaces` 表示呈现范围，不表示执行位置或启用许可。界面扩展的入口和启用目标属于新的界面契约，不直接改变该字段的语义。

## 管理方式

### 一个入口与两个分类

管理入口包含「Harness」和「界面扩展」两个分类。「Harness」沿用目标 Host 的目录、配置与现有管理操作；「界面扩展」统一列出 DSH 兼容插件和未来的原生插件。第一期在 Web 提供界面扩展管理，GUI 中的管理入口随 GUI 扩展接入。

统一入口负责展示和转交操作，各加载器继续拥有自己的配置、校验和生命周期。第一期不迁移 Harness 插件目录、不改变其启用文件，也不把 Harness CLI 安装、Harness 插件安装和界面扩展安装当作同一种操作。

界面扩展记录需要表达以下信息；具体字段名和持久化格式在实施时确定：

| 信息 | 含义 |
| --- | --- |
| 身份和来源 | 稳定扩展身份、接入格式、原始包名、版本和安装来源；来源与格式分开，npm 不等于 DSH |
| 支持范围 | 插件入口与宿主兼容检查共同确定的 Web、GUI 支持情况 |
| 启用范围 | 用户在支持范围内选择的目标，按所属宿主保存 |
| 兼容情况 | 针对插件版本和宿主基线的已验证、未验证或不支持结论，以及具体原因 |
| 实际运行情况 | 每个目标分别记录加载结果和错误；配置已启用不代表已经加载成功 |
| 配置与生效方式 | 插件实际支持的配置、保存位置，以及是否需要重启或刷新 |

版本和声明依赖满足只表示通过相应检查，不自动获得「已验证」标记。未验证插件显示实际检查和加载结果；已发现必需服务缺失或版本冲突的插件不得激活。

### 作者支持范围与用户选择

| 作者提供且宿主支持的入口 | 用户可以选择 |
| --- | --- |
| 仅 Web | 在 Web 启用或禁用 |
| 仅 GUI | 在 GUI 启用或禁用 |
| Web 和 GUI | 两端均禁用、仅 Web、仅 GUI、两端均启用 |

用户启用的目标必须是支持目标的子集。第一期 DSH 兼容插件仅支持 Web，不能通过勾选 GUI 获得跨端能力。原生插件将来可以提供独立的 Web、GUI 入口，共享业务代码由作者自行决定。

作者声明、用户选择和当前加载结果分别保留。某端加载失败只改变该端运行结果，不悄悄改写插件声明或用户的启用选择。

每端分别激活和释放界面资源。关闭 Web 页面或在 Web 禁用插件，不应停用 GUI 入口；整包卸载属于另一项操作，需要明确影响哪些目标并完成对应清理。

### 安装与配置归属

界面扩展使用独立于 Harness 插件的安装记录和数据目录。第一期由 Web 服务管理，安装包及启用配置位于其持久数据目录，产品升级不得覆盖。内置插件由产品发行管理，用户插件不能通过同名包静默替换内置运行时。

安装和启用作用于所管理的 Web 服务，影响连接该服务的页面；它们不是当前浏览器独有的开关。主题选择等个人偏好沿用浏览器本地存储。插件配置按其原生契约接入真实的配置读写，不将任意插件配置一律改存浏览器，也不以空实现冒充 DSH 配置服务。

安装、启停和卸载入口沿用本机管理边界，在服务端检查权限；远程访问令牌不会因此自动获得插件管理权限。将来 GUI 拥有自己的运行和启用状态，同一包在两端出现不意味着跨机器或跨宿主自动同步配置。

## 模块职责与复用方式

| 所有者 | 职责 |
| --- | --- |
| codexhost 扩展管理 | 管理身份、安装结果、启用目标、配置入口与各端状态，将操作交给实际所有者 |
| DSH 兼容模块 | 读取原生包及 bundle 声明，检查依赖，通过 Cordis Loader/Include 和 ClientModules 加载前后端贡献 |
| Web 扩展宿主 | 持有监听器、认证和核心路由；嵌入原生 webServer，管理服务端与页面的加载、清理及恢复 |
| GUI 扩展宿主 | 由 `renderer-extension` 提供明确扩展位置；Codex 私有 DOM、React 绑定及版本检查由宿主维护，CDP 和进程交互由 `desktop-control` 等现有所有者维护 |
| Harness 插件运行时 | 保持现有 Adapter 公共契约、目标 Host 所有权和 Thread 执行归属 |

Cordis、依赖注入、生命周期、客户端模块格式、主题接口和 UI 插槽可以直接复用。插件安装记录、外置资源发现、管理页面和失败恢复由 codexhost 接通。现有 DSH 插件管理器依赖完整后台，按所需能力复用，不把恢复整套后台作为纯前端兼容的前提。

DSH 的 `ctx`、Session、bundle patch 等实现细节收在兼容模块中，不进入 codexhost 的公共 Host 或 Harness 契约。原生界面扩展需要的公共接口按真实用例增加。公共数据契约保持浏览器安全，Web 和 GUI 客户端不导入 Node、Electron 私有 API 或 Harness SDK。

## 第一期支持范围

第一期目标是安装未经修改的 DSH 客户端发布包，通过现有公开接口扩展 Web，并完成重启恢复、禁用和卸载。兼容对象以原包版本和已验证宿主基线为单位。

当前具备本机管理、npm 包名/GitHub 仓库/本机目录/归档安装、安装源选择、原生前后端装配、宿主版本校验、启停与卸载，以及独立恢复页、单页仅内置模式和整服务安全模式。Maid Atelier、Open Sea 和 Blackgold 的原包展示、资源及恢复验证范围见[功能文档](../product/web-ui-extensions.md#原包验证范围)，其中也记录尚未通过的核心回归。资源由原包服务端路由提供，不增加逐插件映射。通用配置编辑、自定义主题选择与持久化、其他面板/展示样本尚未完成。下表描述第一期的完整目标。

| 插件能力 | 第一期支持条件 |
| --- | --- |
| 主题和皮肤 | 使用主题注册或 token 接口；支持自定义主题选择、保存、刷新恢复和禁用后的内置主题回退 |
| 独立页面和侧栏入口 | 通过已有 list 或 keyed 插槽追加内容，使用独立身份，不替换核心界面 |
| 右侧栏标签页 | 使用已有 tab 注册与导航接口，验证会话绑定、切换、关闭和清理；不要求新增服务端能力 |
| 展示组件 | 消费当前实际提供的数据结构；缺失字段有正常表现，不制造 Harness 没有提供的数据 |

已有数据展示不授予新的会话写入或执行能力。插件使用的现有查询、导航和界面操作按具体契约核对，不从 DSH Session 类型推断其他 Harness 的能力。

布局兼容限于现有插槽中的增量扩展。整套布局、整个侧栏或聊天主树的替换，以及依赖私有 DOM 层级或 CSS 类名的插件，不纳入第一期兼容承诺。现有页面可继续演进，已承诺的插槽名称、作用域、传参和主题接口需要保持契约。

兼容按真实依赖判断，不按包名或界面外观判断。存在 `./client` 入口并不充分：服务端入口可能提供必需的配置、启动 globals 或资源注册。普通 Web 启动执行已启用包的原生 Host 入口和 bundle；安装与保存启用选择本身不执行。缺失服务明确报告，不自动裁掉必需后台部分，也不为此启动 DSH Agent Runtime。

### 安装加载与配置

- 沿用 DSH 的添加插件体验，支持直接输入 npm 包名、GitHub 仓库地址、本机目录或安装包，选择官方、镜像或自定义 npm 源，记录实际安装版本。目录安装保存独立副本。消费已构建的客户端产物，不要求在 codexhost 源码仓库重新编译。获取和安装包及其依赖时不执行生命周期或构建脚本；依赖脚本生成资源或启动新 Node 服务的包报告不支持。
- 安装到暂存位置，完成包结构、入口、资源路径、依赖和版本检查后再登记。安装失败保留此前可用组合，安装完成与启用分开记录。
- 保持 DSH 原生客户端 manifest 和模块格式，将内置插件与已启用用户插件组成同一启动图，复用共享 React、Cordis 和插槽模块。依赖闭包和包身份冲突必须明确诊断。
- 通过原生 ClientModules 提供 JS 分块，配套资源由原包 webServer 路由处理，保留其方法和缓存语义。用户装配不能覆盖内置模块、服务、认证、核心路由或恢复入口。
- 补齐自定义主题的选择器、持久化和首屏恢复。第三方配置必须有可用 schema、存储和运行时消费路径，缺少必要路径时报告不支持。
- 安装、配置或启停变化通过重启 Web 和刷新页面生效，界面显示待生效状态。应用插件变化不需要重启 CH Host；Web 重启会中断自身连接与终端，沿用其现有生命周期提示。

Web 插件可在现有后端 Context 中注册其 Web 服务和路由，不另开产品监听端口；Harness 执行和 Thread 持久化仍由原所有者负责。依赖安装脚本生成后台产物、或要求未提供的 Agent 服务的包不在当前支持范围。

### 管理与失败恢复

管理页面提供列表、安装、启用、禁用、卸载，以及版本、兼容情况和错误原因。插件异常不能使恢复路径依赖同一个失败的插件图；提供只加载内置插件的启动或恢复入口。

客户端启动检查需要区分内置插件故障与可选插件故障，并处理依赖失败的插件。禁用后重新加载时，注册的组件、样式、订阅和事件应被释放，不留下悬空界面。保留上一份可用配置用于恢复，不自动反复激活失败版本。

插件是同进程、同页面的可信代码，不增加沙箱、权限系统或运行审批。Cordis 负责生命周期清理，不承诺撤销任意外部副作用。`--safe-mode` 在导入用户代码前生效；`/extensions` 和 `?extensions=off` 不执行用户客户端或首页注入，但不会停止已运行的服务端入口。卸载先移除登记，文件在运行实例释放后清理；下次启动清理残留。已启用的含 Host 入口包会在下一次普通 Web 启动时执行服务端代码。

### 第一期之外

- 独立 DSH Agent 后台，以及面向其执行体系的通用 RPC 和动态执行兼容层。
- DSH 工具、模型 Provider、Agent hooks、工作流、调度和会话持久化插件的统一接入。
- 原生 DSH profile 的插件管理、混合插件的自定义 UI 桥接，以及对其他 Harness 的工具转换。
- codexhost 原生界面插件加载器、公开跨端 SDK、GUI 第三方扩展运行时。
- 全量插件市场、自动升级、运行中热替换和无刷新生效。

## 实施顺序与验收

先选择主题、追加面板和展示组件三类真实发布包，固定版本并核对依赖。若样本需要未支持的后台能力，应调整样本或显式调整范围，不能通过修改插件源码绕过验收目标。

| 步骤 | 工作 | 完成标准 |
| --- | --- | --- |
| 1 | 确定样本和兼容基线 | 记录原包版本、客户端入口、资源、配置和服务依赖，明确可用接口及不支持原因 |
| 2 | 外置包发现和资源装配 | 原包不改源码，不改固定插件清单，不重建产品，在源码与发行模式均可加载 |
| 3 | 主题与 UI 契约接通 | 自定义主题刷新保留且禁用可回退；页面、侧栏和展示组件在桌面及手机布局下正常；会话切换和关闭无残留 |
| 4 | 管理与恢复 | 安装、配置、启停和卸载可完成；缺依赖、包损坏、版本冲突和插件异常有明确诊断，可恢复内置界面 |
| 5 | 发行和生命周期验收 | 在仓库外运行发行包，不依赖源码、开发 watcher 或未打包依赖；配置重启保留，资源路径受限，远程调用不能越过管理权限 |

检查还应覆盖相同包身份冲突、依赖失败传播、缺少展示字段、主题加载顺序，以及当前 Web 改动与插件共存。仅编译成功或模块注册成功不算完成兼容验收。

## 原生插件和 GUI 接入预留

第一期管理记录和模块边界需要保留类别、格式、安装所有者、支持目标、启用目标及各端运行结果；此处定义信息语义，不提前发布尚无消费者的完整 manifest 或 SDK。

后续第一个原生插件应以实际功能确定最小入口契约。一个包可以只有 Web 入口、只有 GUI 入口，或同时提供两个入口；共享数据和业务逻辑可复用，两端 UI 代码无需相同。现有[设置页挂载契约](../../packages/renderer-extension/src/settings/core.ts)与[Web 设置入口](../../packages/renderer-extension/src/web-settings-entry.ts)可作为复用实例，不直接当作完整第三方插件 API 发布。

GUI 接入时，由宿主提供面板、设置项或按钮等明确位置和受限的操作接口。第三方插件不自行追踪 Codex 私有 DOM、React 状态或 CDP；相关绑定由 `renderer-extension` 和 `desktop-control` 集中维护。某版本缺少必要挂载条件时，报告该 GUI 扩展不可用，不接管官方 Thread 执行路径。

DSH 插件保持 Web 兼容来源的定位，不自动成为 GUI 插件。若以后出现可共享的主题数据或界面组件，按实际 GUI 契约接入并单独验证。包文件和配置是否共享由具体所有者确定，跨端启停、运行状态和故障始终分别处理。
