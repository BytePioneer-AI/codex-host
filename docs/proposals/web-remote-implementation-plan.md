# Web 远程访问实施计划

> 状态：执行中，阶段 1、2 已完成。本文是实施远程访问的总体安排，每个阶段都以本文为起点。
>
> 要做成什么样、为什么这样做，见[总体设计](web-remote-relay-architecture.md)；第一版不做的方案，见[暂缓方案记录](web-remote-deferred-options.md)。协议、接口和参数由各阶段的 OpenSpec change 确定。

## 1. 目标

用户在手机浏览器或 PWA 上，从任意网络连接自己电脑上的 Agent，手机不用安装额外软件。第一版提供五种访问方式：局域网、Tailscale、官方中转、自托管中转、自备隧道。

## 3. 依赖和顺序

```text
1 → 2 → 技术用户可用
1 → 4 ──┐
3 ──────┴→ 5 → 6 → 7
```

- 阶段 3 尽早做。它成本低，却决定最大的那笔投入。
- 阶段 3 和阶段 4 互不依赖，可以同时进行。
- 阶段 4 不等中转，Tailscale 用户同样需要关掉终端后还能访问。
- 阶段 2 只做基本功能，主要精力留给阶段 3–6。Web 进入安装包前，能运行 Web 的只有源码用户，所以一键开启 Serve 放到阶段 4。
- 建议先收尾阶段 1，再做阶段 2，然后做阶段 4。

## 4. 工作方式

1. 每个阶段开始前，先对照最新代码核对本文和总体设计。文中的代码现状可能已变化。
2. 每个阶段写一个 OpenSpec change，阶段 5 拆成三个。阶段 3 不写产品代码，产出验证报告。
3. 每个阶段按第 5 节的完成标准验收，真机验收的结果要写明，未执行的检查不算通过。
4. 阶段完成后，更新第 2 节的状态和对应的产品文档，并把相关内容从“拟议”改为当前行为。
5. 范围或顺序有变化时，先改本文，再改 OpenSpec change。

OpenSpec change 名称为建议值，创建时可以调整。

## 5. 各阶段

### 阶段 1：Token 认证

**OpenSpec：** [`add-web-remote-token-auth`](../../openspec/changes/archive/2026-11-04-add-web-remote-token-auth/proposal.md)

**交付：**

- 一个访问 token，保存明文；本机页面显示登录二维码和链接，可随时复制，并显示最近使用时间。
- 重新生成 token 时立即拒绝旧 token 的 HTTP 请求，主动断开它的所有 WebSocket 和事件流，并删除它的推送订阅；运行中的任务不停止。
- 其他设备可退出登录，只影响当前浏览器。
- 登录页、带 token 的链接，以及读取后从地址栏移除 token。
- Web 设置中的“连接设备”页；非本机访问时显示提示，不显示 token，接口拒绝。
- 启动时输出带本机 token 的本机链接，自动打开浏览器由阶段 4 的统一启动命令负责。本机 token 不在界面中展示，只在本机访问条件下有效。
- 可信代理配置：只有显式配置时才信任 `x-forwarded-*`。
- 下载和预览的安全处理、登录失败限速。
- 局域网改用访问 token，`npm start web` 保持默认监听 `0.0.0.0`；界面提示明文风险。

**实施时要处理：** 总体设计 4.4 把“已通过 token 登录”列为本机访问条件之一，而本机 token 本身要先满足本机访问条件才有效。本机 token 的校验只看其余三条（回环地址、`Host`、没有转发头）。

**由 Spec 决定：** token 的长度和格式、是否支持过期时间、链接格式、现有 `?token=` 链接的兼容方式、下载和预览的隔离方式。

**完成标准：**

- 重新生成 token 立即断开旧 token 的所有连接，不影响这台电脑。
- 非本机访问能看到菜单和提示，但看不到 token，接口被拒绝，包括经 Tailscale Serve 和 frp 转发的请求。
- 换一个浏览器后，重新运行启动命令可以恢复本机登录。
- 关闭界面或重启 Web 后台不影响 Host 和运行中的任务。

### 阶段 2：Tailscale 和自备隧道

**前置：** 阶段 1

**OpenSpec：** [`add-web-remote-tailscale-access`](../../openspec/changes/archive/2026-11-05-add-web-remote-tailscale-access/proposal.md)

**交付：**

- 只读检测 Tailscale 是否已安装、已登录，以及 Serve 是否已转发到当前 Web，不修改 Tailscale 配置。
- 检测到 Serve 转发时自动配置可信代理，提供访问地址、二维码和连接诊断；未转发时显示可复制的开启命令。
- 手机端显示连接状态：无网络、连接中、电脑离线、Host 未就绪、恢复中、已连接、token 已失效。
- 自备隧道的配置项（公开地址、可信代理）和文档，覆盖 frp、Tailscale Funnel、Cloudflare Tunnel、nginx。

**实现状态：** 只读状态与信任刷新、公开地址、连接设备页和电脑离线提示已实现并通过聚焦自动化验证，使用方式见[Web 远程访问](../product/web-remote-access.md)。用户确认实际使用 Tailscale 没有问题，并决定不再继续其他验收；未分平台记录，切网、锁屏和电脑离线后恢复未单独记录，nginx、frp、Cloudflare Tunnel 示例未实际运行。

**完成标准：** 手机从蜂窝网通过 Serve 完成登录和日常操作，切网和锁屏后能恢复，且没有重复消息。

这一阶段完成后，能从源码运行 Web 的技术用户可以稳定使用。Web 服务仍随终端运行，要保持终端打开、电脑不休眠。

### 阶段 3：可行性验证

**产出：** 验证报告和继续与否的决定，不写产品代码。

**验证内容：** 用一台香港 VPS、一个临时域名和手动证书搭建 SNI 转发原型，验证：

- 三大运营商蜂窝网和办公网的连通性，以及手机开着代理时的情况。
- WebSocket 和事件流的长时间稳定性、锁屏恢复、切网恢复。
- 真实延迟和流量，用于确定额度和成本。
- TLS-ALPN-01 能否通过 SNI 转发完成。
- 出站连接选 WSS 还是原始 TCP，以及代理环境下的可达性。
- Web Push 在大陆的可用性，包括 Android 和电脑端的出站。
- SniTun 的许可证和代码质量，决定复用还是自己实现。
- 境内外部署的合规要求。

**决策点：** 实测不理想时，先调整线路和域名；仍然不行就暂缓阶段 5–7 中的官方中转，继续提供其余访问方式。是否仍做自托管中转到时单独决定。

### 阶段 4：统一启动和 Web 常驻

**前置：** 阶段 1

**OpenSpec：** [`add-web-background-service`](../../openspec/changes/add-web-background-service/proposal.md)

**交付：**

- Web 服务进入安装包和 npm 包。
- 提供下表的命令。开发命令不变，继续在前台运行，保留日志和热更新。

| 命令 | 行为 |
| --- | --- |
| `codexhost` | 确保 Host 和 Web 在后台运行，再打开 GUI |
| `codexhost web` | 确保 Host 和 Web 在后台运行，再打开浏览器；没有图形界面时只输出地址；输出“已在后台运行，用 `codexhost stop` 停止” |
| `codexhost stop` | 不确认，直接关闭 codexhost 拉起的 GUI、Web、Host、远程服务、Broker 和 Console，并输出被中断的任务数 |
| `codexhost status` | 只读显示 Host/Web 状态与版本、不带 token 的访问地址、最近 Web 失败原因和自启项是否有效 |
| `codexhost autostart on\|off\|status` | 开启、关闭或查看当前用户的登录自启；不改变当前服务运行状态 |

- 关闭终端、GUI 窗口或浏览器后，Host 和 Web 后台继续运行。
- Web 后台默认只监听 `127.0.0.1`，用户在设置中开启入口后才对外。开启时重启 Web，运行中的任务不受影响，Web 终端会断开。
- 重复运行或换一条命令时，复用已运行的 Host 和 Web，只打开对应界面，不重启；只有 Host 在运行时补上 Web。
- 端口被其他程序占用时提示失败，可用 `--port` 指定，不自动换端口。`npm start web` 遇到安装版 Web 占用端口时同样提示，不杀进程。
- 由 Rust 负责 Web 后台的启动、监管和退出清理，不解析 token 或 Harness 语义。Web 崩溃后带退避自动重启；启动失败不反复重启。支持 macOS、Windows 和 Linux。
- Web 设置页可在没有 Desktop 的情况下检查和发起更新，界面共享同一更新协调器与互斥；原生层接管安装，纯 Web 更新后不打开 GUI，失败时尽力恢复可用安装并保留实际结果。
- 更新由用户发起，后台只下载和准备。更新时直接重启 Host 和 Web，不判断是否有任务在运行，并输出被中断的任务数。`npm update` 后下次运行 `codexhost` 时，发现版本不一致同样直接重启。同时装了安装包和 npm 版时，以最后运行的为准并提示。
- 登录后自动启动默认关闭，开启远程访问时提供开关，由 `codexhost` 在运行时写入，不在安装时注册；只启动 Host 和 Web，不打开界面。macOS 用用户级 LaunchAgent，Windows 用当前用户的 Run 注册表项，Linux 用 systemd 用户服务，没有 systemd 时不提供。npm 版依赖用户的 Node 路径，每次运行时刷新自启项，路径失效时由 `codexhost status` 报告。
- Windows 卸载先通过安装内的 `codexhost stop` 停止服务，再通过 `codexhost autostart off` 移除自启项，完成页提示 Serve 配置保留。覆盖安装不执行卸载动作；macOS/npm 的等效步骤见[卸载与回退](../product/standalone-web.md#卸载与回退)。
- `npm stop` 识别后台 Web 监管进程和 Web 子进程，先停监管进程防止重启，再停 Web，然后才停 Host；沿用进程身份复核、发信号与等待退出，不按端口或进程名猜测。
- 电脑端的“手机远程访问”设置入口，以及后台运行状态。
- 用户确认后一键开启和关闭 Tailscale Serve。开启前检查根路径，已转发到别处时不覆盖；关闭只移除指向当前 Web 的根路径；结果以重新读取的状态为准。按 Tailscale v1.104.1 源码，`--bg` 会直接替换同路径转发，不带 `--set-path` 的 `off` 会删除该端口所有路径，缺少 HTTPS 能力时命令可能退出码为 0 却没有写入配置。

**Spec 中的决定：**发行包不带 LibreOffice 引擎，第一次预览时从 npm 官方源下载；Web 退出、停止和更新都不撤销 Serve；`codexhost stop` 关闭 codexhost 的全部进程（用户自己打开的 Codex Desktop 除外）；`codexhost web` 的 `--host`、`--port`、`--public-url`、`--trusted-proxy` 保存后用于之后的启动。

**验收场景：**

| 场景 | 预期 |
| --- | --- |
| 第一次运行 `codexhost` | 拉起 Host、Web 和 GUI，Web 只监听本机 |
| 没装 Codex Desktop 就运行 `codexhost` | 提示未安装，并打开 Web |
| 从 Finder 或开始菜单打开 | 与 `codexhost` 相同，状态显示在界面上 |
| SSH 登录后运行 `codexhost web` | 不打开浏览器，只输出地址 |
| 已运行 `codexhost web`，再运行 `codexhost` | 只打开 GUI，任务不中断 |
| GUI 已打开，再运行 `codexhost` | 切到前台，不重启；实施前核实现状 |
| 两个终端同时启动 | 只启动一份，另一个等待后复用 |
| Web 崩溃 | 自动重启，任务不受影响 |
| Host 崩溃 | Web 重新拉起 Host；中断的任务不自动继续 |
| 电脑休眠或合盖 | 手机显示电脑离线，唤醒后自动恢复，并提示调整休眠设置 |
| 电脑重启 | 没开自启时离线；开了自启，登录后恢复（Linux 开启 linger 后开机即恢复）；中断的任务不自动重发 |
| 只用手机时有新版本 | 不自动重启，等用户发起更新 |
| 卸载 | 停止服务，移除自启项，并提醒 Tailscale Serve 配置还在 |
| Windows 覆盖安装 | 安装准备关闭占用文件的进程，不执行卸载动作，不关闭自启 |
| 后台 Web 占用 4400，运行 `npm start web` | 提示端口占用并退出，不结束后台 Web、不自动换端口 |
| 在未构建的工作树运行 `npm stop` | 校验并停止后台 Web 监管进程和子进程，再停止 Host；配置和数据保留 |

**完成标准：**

- 关闭终端后，手机仍能连接并继续操作。
- 重启 Web 后台不重启 Host，也不影响运行中的任务。
- 更新后 Host 和 Web 都运行新版本，会话记录保留。
- 测量并记录空闲时 Web 后台的内存和 CPU 占用。

### 阶段 5：中转核心

**前置：** 阶段 1、阶段 3 决定继续、阶段 4

**OpenSpec：** 拆成三个，按顺序进行。

| Change | 内容 |
| --- | --- |
| `add-remote-relay-server` | 新包 `packages/remote-relay/`：校验电脑身份、防止抢占子域、按 SNI 路由、多路复用、背压控制、按子域限制带宽和总流量；不持有证书，不落盘内容；纳入 `tools/check-boundaries.mjs` |
| `add-web-remote-relay-client` | 电脑端：身份密钥和子域 ID 派生、出站连接和自动重连、进程内 TLS，把解开后的流量交给现有 HTTP 服务 |
| `add-web-remote-certificates` | 证书申请和续期，优先 TLS-ALPN-01，不可行时改用由 Relay 代写记录的 DNS-01；证书私钥只在用户电脑上；准备备用证书机构 |

前端和设置同步交付：前端壳的离线缓存（曾经访问过的手机能显示离线状态）、中转开关、当前地址和诊断信息。

**由 Spec 决定：** Relay 控制协议、多路复用格式和流控参数，Relay 是否向电脑传递客户端 IP，证书存储位置、续期时机和失败提示，离线缓存范围及其与版本更新的关系，远程功能的版本兼容策略。

**完成标准：**

- 真实 iOS、Android 手机从蜂窝网通过子域名登录，并完成日常操作。
- 电脑换 IP 或 Relay 重启后自动重连，地址和 token 不变，任务继续运行，没有新建原生会话。
- 证书能自动申请和续期，失败时有明确提示。
- 大文件传输不阻塞停止和审批。
- 抓包和 Relay 日志中都不出现业务内容。

### 阶段 6：官方服务上线

**前置：** 阶段 5

**OpenSpec：** `add-official-relay-operations`，只覆盖代码部分。

**交付：**

- 运营功能：内测邀请码、注册频率限制、按 ID 封禁、举报入口。这些功能在自托管时默认关闭。
- 在线状态、容量和异常监控，只记录必要元数据。
- 根据阶段 3 和内测数据确定流量额度；截图和侧栏浏览器推流默认关闭。
- 官网：产品介绍、教程、服务状态、隐私政策。
- 部署 Relay 并开始小范围内测。

**上线前必须完成：**

- 独立域名，并申请 Public Suffix List。
- 修订隐私政策和信任边界说明。
- 证书透明日志监控。
- 安全审查。
- 确认合规要求。

**完成标准：**

- 内测用户只凭地址和 token，就能在真实手机上完成日常操作。
- 超出额度时有明确提示，不影响电脑上的任务。
- 服务故障不影响运行中的任务和其他访问方式。

### 阶段 7：开放自托管

**前置：** 阶段 5。不依赖阶段 6 的运营功能，但等官方服务稳定后再开放。

**OpenSpec：** `add-self-hosted-relay`

**交付：** 公开 Relay 源码、Docker 镜像、compose 示例和一页部署文档；支持配置自己的域名和 Relay 地址。不提供单独的安装器或管理后台。

**完成标准：** 按文档从零部署后，登录方式和官方中转一致。
