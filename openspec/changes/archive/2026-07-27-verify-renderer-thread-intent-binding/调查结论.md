# Renderer Thread 意图绑定调查结论

## 结论摘要

本 change 验证了 Renderer 自定义字段能够随真实 `thread/start` 到达 app-server Observer，但没有完成 Gate B，也不应将当前 direct CDP/private Renderer seam 方案继续作为正式产品架构。

当前方案的核心假设是：用户首次发送时，可以在 Renderer 的一个稳定 seam 读取最终 Codex/Pi 选择，并将 `params.codexhost.harnessId` 写入同一个真实创建 Request。实际调查发现，当前可取得且真实触发的 seam 是 `thread-prewarm-start`，它属于 Thread 预热流程，不保证发生在用户最终发送时，也不能可靠表达“发送时最终选择”。

因此当前 change 的状态是：

- 技术调查获得了有效证据；
- Renderer carrier 可达性得到证明；
- Codex/Pi 串行路由 Gate 未通过；
- 当前实现不应作为完成的交付基线；
- 后续方案应改用 app-server 协议中的官方 Model 选择作为路由入口。

## 已验证事实

### 1. 当前 Desktop 与 CLI

调查环境：

```text
Desktop: /Applications/ChatGPT.app
Bundle ID: com.openai.codex
Desktop version: 26.721.41059
CLI: /Applications/ChatGPT.app/Contents/Resources/codex
CLI version: codex-cli 0.146.0-alpha.3.1
Node: v24.18.0
```

当前 macOS 安装名已经从历史 `Codex.app` 变为 `ChatGPT.app`，但 Bundle ID 仍为 `com.openai.codex`。

### 2. direct CDP 链路可用

已真实确认：

```text
受控 Desktop 启动
→ process-level remote debugging 参数
→ CDP listener 属于本次 Desktop 进程树
→ Renderer page target
→ WebSocket CDP
→ Runtime.evaluate
```

因此失败不是系统权限、CDP 连接或 Renderer target 不可用造成的。

### 3. 当前 Renderer 的真实创建候选

当前 bundle：

```text
./assets/app-initial-BHB6SClA.js
```

已确认 export：

```text
idt.dispatchMessage
```

真实调用形状：

```text
boundaryType: thread-prewarm-start
requestShape: payload.request.params
createMethod: thread/start
```

对应 bundle 行为：

```text
prewarmThreadStart(params, options)
→ enqueueRequest("thread/start", params, ...)
→ dispatchMessage("thread-prewarm-start", { request, ... })
```

该 wrapper 在一次人工 Codex 创建尝试中实际触发，装饰计数为 `1`。

### 4. 自定义 carrier 已到达真实 Observer

使用：

```text
params.codexhost.harnessId
```

修复 Shim 接管问题后，Observer 记录了以下 allowlist 路由事实：

```json
{
  "type": "create-route",
  "harnessId": "codex",
  "extensionRemoved": true,
  "officialForwarded": true,
  "blockedBeforeOfficial": false
}
```

这证明：

```text
Renderer 当前 Codex 选择
→ thread-prewarm-start 的真实 thread/start Request
→ params.codexhost.harnessId = "codex"
→ Gate Observer
→ 删除整个 params.codexhost
→ 转发官方 app-server
```

所以“未知 namespaced 字段能否从 Renderer 到达 app-server 代理”已经得到真实证据。

### 5. Shim 曾经没有接管真实 app-server

Desktop 的真实 CLI 参数为：

```text
-c features.code_mode_host=true app-server --analytics-default-enabled
```

旧 Shim 只判断：

```text
arguments[0] == "app-server"
```

因此它绕过 Observer，直接启动官方 CLI。这解释了早期多次出现的现象：Renderer wrapper 触发、Codex 对话正常，但 Observer observation 始终为空。

修复全局参数识别后，已真实确认进程链：

```text
codexhost-shim
→ Node 24 tools/gate-b/observer.mjs
→ official codex app-server
```

该事实对后续正式 Host Runtime 仍然有效：识别 Codex 子命令时必须先解析合法全局参数，不能假设子命令位于 `argv[0]`。

## 遇到的问题

### 1. `thread-prewarm-start` 不是发送时 seam

`thread-prewarm-start` 是预热流程，可能早于用户点击发送发生。可能出现：

```text
默认选择 Codex
→ Desktop 预热 thread/start
→ 用户切换 Pi
→ 用户发送时复用预热 Thread
```

此时创建 Request 记录的是预热时选择，而不是发送时最终选择。即使某次 Gate 偶然通过，也不能稳定证明当前 spec 要求的“发送动作发生时读取最终 Harness”。

### 2. Observer 与 Renderer wrapper 存在启动竞态

Observer 从 app-server 启动开始处理 Request，但 CDP 只能在 Renderer target 出现、连接成功并加载模块后安装 wrapper。在 wrapper 安装前产生的目标 Request 不包含 carrier。

当前 Observer 对缺失 carrier 的目标 Request fail-closed，会终止代理链并导致 Desktop 显示：

```text
ChatGPT 已意外停止
```

增加 Observer arming 协议可以缓解 Gate，但会继续扩建 Gate-only 状态机，并不能形成最终产品能力。

### 3. 原地修改共享 Request 对象存在污染风险

当前实验曾原地增加：

```js
request.params.codexhost = { harnessId };
```

该 Request 可能同时被 Renderer queue、Promise registry 和生命周期事件持有。即使 Observer 在 wire 侧删除扩展，Renderer 内部仍可能观察到未知字段。

使用 immutable outbound clone 可以避免该风险，但无法解决预热语义和 wrapper 安装竞态，因此不足以挽救整体方案。

### 4. 私有 Renderer seam 版本敏感

调查中确认或排除过：

- `tdt.getInstance().sendRequest`：HTTP `GET`/`POST` client，不是 app-server Request；
- `electronBridge.sendMessageFromView`：contextBridge binding 不可替换；
- `Rf`（export `ddt`）到私有 `_Ze.sendRequest`：属于另一条 Host RPC facade，不承载本次预热创建；
- `Debugger.setBreakpointOnFunctionCall` 获取 `_Ze`：曾暂停 Renderer 并导致 Codex 卡住，不应保留；
- `idt.dispatchMessage`：可写且会触发，但语义是预热，不是最终发送。

继续依赖 minified export、动态 chunk 和私有生命周期会让每个 Desktop 版本都需要重新调查。

### 5. 当前测试与实验接口发生过多 churn

当前工作区包含多轮 seam 实验留下的测试接口：

- 旧 `sendRequest` seam；
- 旧 Capture 接口；
- `Rf/_Ze` Debugger 实验；
- 恢复后的 `thread-prewarm-start` direct dispatcher。

最后一次 `npm run gate:b:hermetic` 结果为：

```text
10 test files
66 tests total
54 passed
12 failed
```

12 个失败主要是过时测试仍引用已废弃接口。这些失败不应通过恢复废弃实现来解决。当前分支是调查快照，不是绿色交付基线。

## Gate 结果

Gate B 没有达到 `PASS`。

已完成：

- 真实 Renderer 控件和 carrier 装饰；
- carrier 到达 Observer；
- Codex 扩展删除和官方转发事实；
- app-server Observer 真实进程接管。

未完成：

- Codex 转发后保持稳定、可继续对话；
- Pi 真实创建 Request 到达 Observer并在官方 Agent Loop 前拦截；
- 窄范围最终 `PASS`报告。

因此 tasks 5.1–5.3 不能勾选，3.2 只能解释为“carrier 可达已证明”，不能解释为“发送时最终选择语义已证明”。

## 不再推荐的正式方案

不建议继续发展：

```text
direct CDP 注入自定义 Harness 控件
→ private Renderer prewarm seam
→ params.codexhost.harnessId
→ Gate-only Observer 删除扩展
```

它可以作为兼容性调查工具，但不应成为 codexhost 的正式路由架构。

## 推荐的后续方案

改用 app-server Host Facade：

```text
官方 model/list Response 增加 Pi 路由条目
→ 用户通过 Codex 原生 Model 选择器选择 Pi
→ thread/start.params.model 携带保留的 Pi route ID
→ Host Runtime 按 Model route ID 选择 Codex 或 Pi
```

Codex：

```text
官方 Model
→ Request/Response 透明转发官方 app-server
```

Pi：

```text
codexhost/pi/* route ID
→ Host Runtime 不转发官方 thread/start
→ 创建 codexhost Thread
→ turn/start 调用本地 pi --mode rpc
→ Pi text_delta 投影为 Codex app-server 事件
```

领域内部仍必须区分 Harness、Provider 和 Model。`codexhost/pi/*` 只是借用官方 `model` 字段作为稳定的 UI/协议路由令牌，不表示 Pi 在领域模型中是一个 Model。

## 建议保留的代码与事实

### 可直接复用

- `/Applications/ChatGPT.app` 与历史 `/Applications/Codex.app` 的安装发现；
- Desktop/CLI 版本和 Bundle identity 检查；
- Pi RPC 已有基础；
- 已有透明 Shim 与进程监督中独立成立的部分。

### 在新方案中重新实现

- 解析 Codex 全局参数后识别 `app-server` 子命令；
- 正式 Host Runtime 的 app-server JSONL 双向转发；
- 背压、EOF、子进程退出和受限诊断；
- `model/list` Response 增强；
- `thread/start.model` 路由；
- Pi Thread/Turn 协议投影。

这些实现应使用正式模块和环境变量命名，不继续依赖 `CODEXHOST_GATE_B_*`。

### 仅保留在本调查分支

- `tools/gate-b` Renderer carrier 实现；
- `thread-prewarm-start` wrapper；
- dynamic seam Capture；
- Gate-only Observer carrier 语义；
- `Rf/_Ze` 调查历史和相关过时测试；
- Gate B native helper 和交互 runner。

## 分支定位

本分支用于保存失败方案、运行证据和调查代码，便于后续查阅，不应作为新方案的开发基线，也不应直接合并到 `main`。

新方案应从干净 `main` 开始，以新的 OpenSpec change 作为唯一实现依据。旧 change 应在新 change 明确 supersede 关系后归档，不能标记为已完成。
