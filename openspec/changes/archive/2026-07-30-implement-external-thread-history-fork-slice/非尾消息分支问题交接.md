# Pi 非尾消息分支问题交接

## 1. 结论摘要

截至 2026-07-29，真实 Codex Desktop 手工测试、当前 Codex TypeScript bindings 和受支持 macOS Desktop `26.721.41059` 静态代码共同确认：

- 对 Pi Thread 的最后一个已完成回答执行原生“从这里继续新任务”可以成功。
- 对较早回答执行相同操作时，Desktop 先发送无边界 `thread/fork`，因此 Host 正确创建来源尾部的临时派生 Thread。
- Desktop 随后对该派生 Thread 发送 `thread/rollback { numTurns }`；`numTurns` 精确等于目标 Turn 之后的 Turn 数。
- 原实现没有接管 external `thread/rollback`，请求落到官方 app-server，导致临时派生 Thread 保留完整来源历史。
- Pi native non-tail Fork 和 Historical Turn 投影都不是这条故障链路的首要根因。

当前实现已增加 bounded post-Fork rollback：只有仍等于来源前缀、尚未独立续聊的派生 external Thread 才能本地执行。Host 从来源目标序号的真实 Checkpoint 创建最终 Native Session，原子替换派生 Thread 的 Native refs 与 `forkSource`，并保留派生 Host Thread ID 和 retained Host Turn IDs。

不要用“非尾请求默认选择前一个 Turn”等启发式方式修复。边界必须来自严格的 `numTurns` 和持久化有序 Turn mappings；Renderer 不监听 DOM 点击，也不按请求时序关联。

## 2. 用户可见现象

测试来源是一个新建 Pi Thread，连续完成三个 Turn。

1. 点击第三个回答的“从这里继续新任务”：成功创建派生 Thread。
2. 在该派生 Thread 中继续一轮：成功，派生记录从 3 个 Turn 增长到 4 个 Turn。
3. 回到三 Turn 来源并点击较早回答的同一原生操作：没有得到按旧回答截断的历史；用户判断为失败。

当前调查没有保存 Prompt、回复正文、Native Session ID、Host Thread ID 或 Host Turn ID。

## 4. 相关代码路径

### 4.1 Desktop 请求解码

文件：`packages/protocol-core/src/thread-fork.ts`

`decodeThreadForkRequest()` 接受当前生成协议中的：

- `lastTurnId`
- `beforeTurnId`
- 两者都省略时表示 tail Fork

`decodeThreadRollbackRequest()` 只接受当前生成协议中的非空 `threadId` 和正安全整数 `numTurns`。官方 Thread 请求不会提前解码，保持原始 frame 透传。

### 4.2 Host 边界选择与派生替换

文件：

- `packages/host-runtime/src/external-thread-fork.ts`
- `packages/host-runtime/src/external-thread-rollback.ts`

直接 Fork 的选择规则保持不变：

```text
有 lastTurnId   -> 查找该 Host Turn
有 beforeTurnId -> 查找前一个 Host Turn
都没有          -> mappings.length - 1
```

Desktop 旧回答路径先命中第三种规则，再由 `executeExternalThreadRollback()` 精确处理。后者验证派生 Thread 仍是其 `forkSource` 对应的来源前缀，计算 `retainedCount = derivedTurnCount - numTurns`，从来源同序号 Checkpoint 创建最终 Session，然后通过 Store 单次原子替换和 Runtime Session 切换保持同一个派生 Host Thread。

### 4.3 Historical Turn 投影

文件：`packages/protocol-core/src/codex-ui-projector.ts`

`projectHistoricalTurn()` 为每个 Snapshot Turn 投影独立 `turn.id`，并生成 User Message 和 Agent Message Items。需要重点确认当前 Desktop 的“从这里继续新任务”动作从哪个 React/UI 实体提取边界：

- 它是否读取包含该 Agent Message 的 `turn.id`；
- 它是否只读取当前 Thread 的最后 Turn；
- 它是否对 `startedAt/completedAt = null` 或历史 Item 结构采用了 fallback；
- 它实际发送的字段是否仍是当前生成绑定中的 `lastTurnId`/`beforeTurnId`。

Desktop 静态代码已经证明 action handler 能用 `targetTurnId` 在完整 Turn 列表中找到准确序号；旧 Turn 选择没有丢失，而是被编码到后续 rollback 的 `numTurns`。因此这些投影差异不再是当前修复的前置假设。

### 4.4 Pi native 边界

文件：

- `packages/adapters/pi/src/pi-history.ts`
- `packages/adapters/pi/src/pi-adapter.ts`

只有 Host 已选择真实 Checkpoint 后，Pi 才会执行：

```text
非尾 Checkpoint -> fork(next active User Entry ID)
尾 Checkpoint   -> clone()
```

本轮 Store 中的边界已经是尾 Turn，所以 Pi 执行 Clone 符合当前输入，并非 native 分支选择错误。

## 5. 原因判断

根因已确认：受支持 Desktop 的消息操作不是单个带边界的 `thread/fork`，而是两阶段协议组合。

```text
getCompleteConversationTurns(source)
-> targetTurnId 精确定位目标序号
-> forkConversationFromLatest(source)          // 无边界 tail Fork
-> numTurns = totalTurns - targetIndex - 1
-> thread/rollback(derived, numTurns)           // 精确边界在这里
```

当前生成 bindings 同时确认：

- `ThreadRollbackParams = { threadId, numTurns }`；
- `numTurns` 必须至少为 1；
- rollback 只修改 Thread history，不回滚本地文件；
- `ThreadRollbackResponse` 返回 `turns` 已填充的更新后完整 Thread；
- 该方法已标记 deprecated，因此 direct `lastTurnId`/`beforeTurnId` Fork 支持必须继续保留。

真实 Windows Desktop 是否与静态检查的 macOS build 完全一致，仍由任务 6.3 的脱敏协议捕获确认。

### 独立缺口：重启后的 external Thread 侧边栏聚合

设计把完整 external `thread/list` 聚合列为非目标。已知 Host Thread ID 的 `thread/read/resume/fork` 可以按 Store 恢复，但 Desktop 重启后不保证 external Thread 自动重新出现在原生任务目录。

这会影响重启后手工找到旧 Thread，但不是本轮同一进程内旧回答被解析成尾 Fork 的直接原因。不要把两个问题混成一个修复。
