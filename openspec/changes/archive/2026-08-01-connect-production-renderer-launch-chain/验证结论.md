## 生产链事实

- Launcher使用随机`127.0.0.1` Electron Inspector端口，不启用Chromium remote debugging；
- 私有Node启动`app/desktop-controller.mjs`，Controller只在Control Session完成后输出`ready`；
- Controller通过同一Control Session安装Title Policy、reload主Renderer、确认ownership、安装Draft Prewarm Policy并执行生产IIFE；
- 生产Renderer默认启用Codex、Pi与Claude Code，不读取Claude开发开关；
- 无参数Launcher把Pi作为生产Composer初始Agent传给Controller；Host对未携带外部transport carrier的创建固定使用Codex fallback，Pi与Claude分别由既有transport carrier显式路由；
- 生产Host默认注册Pi和Claude Code Adapter，Host Bundle携带Claude Agent SDK但不携带可选平台Claude Code包或Claude Code可执行文件；
- Finder PATH缺少用户安装目录时，Claude Adapter继续检查`.local`、Claude legacy、NVM versions、Homebrew和Windows用户npm位置；
- Controller安装失败曾真实触发Launcher关闭本次Desktop，证明未留下Stock UI继续运行；冷启动实测的`Uncaught (in promise)`与`Promise was collected`只进行最多三次250ms瞬态重试，结构错误仍立即fail closed；
- 当前新版真实会话中Desktop、Controller、Host Runtime和官方Codex app-server持续运行，Controller/Launcher日志为空；Host进程环境已确认`CODEXHOST_DEFAULT_AGENT=codex`。

## 真实macOS进度

- 用户已确认上一版主Composer显示Codex/Pi Agent控件；最新三Agent版本菜单仍等待用户确认；
- 首轮测试发现旧组合中选择Codex仍进入Pi，根因是无参数Host fallback为Pi而Codex按规格保留官方Model；
- 新组合已改为“可见初始Pi + Host未标记fallback Codex + Pi/Claude显式transport”，自动测试与重新打包通过；
- 新版会话尚未观察到Pi Native Session，页面Codex回答仍等待用户确认；
- Pi与Claude真实首轮、页面locked状态和Renderer reload恢复尚未完成，不得声明生产Renderer Gate全部通过。
