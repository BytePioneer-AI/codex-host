# Pi 非尾消息分支问题交接

## 1. 结论摘要

截至 2026-07-29，真实 Codex Desktop 手工测试得到以下稳定现象：

- 对 Pi Thread 的最后一个已完成回答执行原生“从这里继续新任务”可以成功。
- 派生 Thread 保持 Pi 归属，并且可以独立追加 Turn。
- 对同一个三 Turn 来源 Thread 的较早回答执行相同操作时，Mapping Store 仍记录成“从来源最后一个 Turn 派生”，派生历史保留了完整三 Turn，而不是截断到所选旧回答。
- 因此问题发生在 Pi native non-tail Fork 之前：旧消息对应的 Host Turn 边界没有正确进入 `executeExternalThreadFork()`，或者进入时已经被替换为来源尾 Turn。

当前最强证据不是“Pi 的 `fork(nextUserEntryId)` 失败”，而是“Desktop 消息操作到 Host Fork 边界之间丢失了旧 Turn 选择”。

不要用“非尾请求默认选择前一个 Turn”等启发式方式修复。若请求没有携带可验证边界，Host 无法知道用户点击了哪条消息，猜测会在别的 UI 路径静默 Fork 错上下文。

## 2. 用户可见现象

测试来源是一个新建 Pi Thread，连续完成三个 Turn。

1. 点击第三个回答的“从这里继续新任务”：成功创建派生 Thread。
2. 在该派生 Thread 中继续一轮：成功，派生记录从 3 个 Turn 增长到 4 个 Turn。
3. 回到三 Turn 来源并点击较早回答的同一原生操作：没有得到按旧回答截断的历史；用户判断为失败。

当前调查没有保存 Prompt、回复正文、Native Session ID、Host Thread ID 或 Host Turn ID。

因此当前缺口集中在真实 Desktop 消息操作与 Host 边界输入的连接处。合成协议测试不能覆盖这个连接。

## 4. 相关代码路径

### 4.1 Desktop 请求解码

文件：`packages/protocol-core/src/thread-fork.ts`

`decodeThreadForkRequest()` 只接受当前生成协议中的：

- `lastTurnId`
- `beforeTurnId`
- 两者都省略时表示 tail Fork

若两个字段都不存在，解码结果不会保留任何边界。

### 4.2 Host 边界选择

文件：`packages/host-runtime/src/external-thread-fork.ts`

`executeExternalThreadFork()` 的选择规则是：

```text
有 lastTurnId   -> 查找该 Host Turn
有 beforeTurnId -> 查找前一个 Host Turn
都没有          -> mappings.length - 1
```

本轮旧回答尝试最终落到第三种结果，或者 Desktop 提供的 ID 本身就是尾 Turn ID。

### 4.3 Historical Turn 投影

文件：`packages/protocol-core/src/codex-ui-projector.ts`

`projectHistoricalTurn()` 为每个 Snapshot Turn 投影独立 `turn.id`，并生成 User Message 和 Agent Message Items。需要重点确认当前 Desktop 的“从这里继续新任务”动作从哪个 React/UI 实体提取边界：

- 它是否读取包含该 Agent Message 的 `turn.id`；
- 它是否只读取当前 Thread 的最后 Turn；
- 它是否对 `startedAt/completedAt = null` 或历史 Item 结构采用了 fallback；
- 它实际发送的字段是否仍是当前生成绑定中的 `lastTurnId`/`beforeTurnId`。

现有证据尚不能在这些可能性之间做最终区分。

### 4.4 Pi native 边界

文件：

- `packages/adapters/pi/src/pi-history.ts`
- `packages/adapters/pi/src/pi-adapter.ts`

只有 Host 已选择真实 Checkpoint 后，Pi 才会执行：

```text
非尾 Checkpoint -> fork(next active User Entry ID)
尾 Checkpoint   -> clone()
```

本轮 Store 中的边界已经是尾 Turn，所以 Pi 执行 Clone 符合当前输入，并非 native 分支选择错误。

## 5. 原因判断

### 高概率：消息动作请求没有携带所点击旧 Turn 的边界

依据：旧回答尝试的持久化 `forkSource` 明确指向尾 Turn，而旧 Turn Checkpoint 存在。

仍需通过原始 `thread/fork` frame 的脱敏字段捕获确认：

```json
{
  "method": "thread/fork",
  "parameterKeys": ["..."],
  "hasLastTurnId": true,
  "hasBeforeTurnId": false,
  "boundaryMatchesClickedOrdinal": false
}
```

捕获时只能保存键、类型、布尔不变量和序号比较，不能保存真实 ID 或会话内容。

### 中高概率：投影历史消息与 Desktop Turn 上下文的关联不满足当前 UI

如果原始 frame 带有边界但总是尾 Turn ID，则需要检查历史 Turn/Item 投影，使每个旧回答的动作闭包绑定到所属 Turn，而不是 Thread 当前尾 Turn。

`projectHistoricalTurn()` 当前的 `startedAt`、`completedAt`、`durationMs` 均为 `null`，Item ID 由 Adapter/Host 合成。尚无证据证明这些字段直接导致问题，但它们是与官方 Codex Thread 值做差异比较时的优先检查项。

### 低概率：Pi non-tail native Fork 本身失败

该假设与本轮 Store 证据不符：Host 选择的已经是尾 Checkpoint，而且真实 Pi non-tail Gate 以前通过。只有捕获到正确旧 Turn 边界进入 Host 后仍收到 `checkpointNotFound` 或 native failure，才应重新调查 Pi。

### 独立缺口：重启后的 external Thread 侧边栏聚合

设计把完整 external `thread/list` 聚合列为非目标。已知 Host Thread ID 的 `thread/read/resume/fork` 可以按 Store 恢复，但 Desktop 重启后不保证 external Thread 自动重新出现在原生任务目录。

这会影响重启后手工找到旧 Thread，但不是本轮同一进程内旧回答被解析成尾 Fork 的直接原因。不要把两个问题混成一个修复。

## 6. 最短后续调查路径

1. 在 Desktop 到 Host 的 NDJSON 边界增加一次性脱敏观测，不改 DOM 点击，不记录参数值。
2. 创建三 Turn Pi Thread，分别点击第一、第二、第三个回答。
3. 每次记录：参数键、边界字段是否存在、边界字段类型、边界是否等于所点击 Turn 序号、Store 最终 `forkSource` 序号。
4. 若第一/第二次请求无边界：检查当前 Desktop 原生 action handler 需要哪些 Thread/Turn 投影条件；不要在 Host 猜边界。
5. 若请求有边界但值总是尾 Turn：对官方 Codex 三 Turn 的 action payload 与 external 投影做差异比较，优先比较 Turn/Item identity 和 action 所在 React props。
6. 若请求边界正确但 Host 变成尾 Turn：修复 decoder/Host 传递并补真实 frame fixture。
7. 修复后增加真实 UI Gate：来源 3 Turn，点击第 1 个回答后派生必须恰好 1 Turn；点击第 2 个必须恰好 2 Turn；点击第 3 个必须恰好 3 Turn。

## 7. 不可接受的临时方案

- 监听消息按钮 DOM 点击并旁路传递 Turn ID。
- 新增自定义 Fork 按钮。
- 请求没有边界时默认选择倒数第二个 Turn。
- 从可见消息文本推断所点击 Turn。
- 复制来源 Transcript 创建派生 Session。
- non-tail 失败后静默回退为 tail Clone 或官方 Codex Fork。
