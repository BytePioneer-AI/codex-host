# 验证结论

## 结论

截至2026-07-29，本Change的Adapter、Protocol、Host和受控Renderer实现已完成。真实Claude Agent SDK Adapter Gate、真实Claude到Host JSON-RPC投影Gate和真实Codex Desktop Gate通过。Desktop已证明Claude开发选项、Model-state绑定、标题隔离、Thread创建路由、普通文本可见、Question回答后文本可见、点击停止及同Thread续轮。

该能力仍是显式启用的开发Gate。默认Renderer只启用Codex/Pi，默认Host只注册Pi，Pi仍是公开MVP的唯一外部Harness。

随后为人工验证Claude Code coding-agent行为，生产SDK Query改为省略`tools`选项并继承Claude Code默认工具集；后续Question Change进一步使用`permissionMode: "default"`，只把原生`AskUserQuestion`映射为Question，并明确deny其他需人工权限的Tool Callback。当前仍不投影普通Tool、File Change或Approval生命周期。

## 真实Desktop受控Gate

受控Gate使用显式Host与Renderer Claude开关。脱敏状态证明：

- Renderer enabled Agent列表为Codex、Pi、Claude Code；
- Renderer Adapter状态为`ready`，使用既有Model-state hook；
- Claude Composer提交后状态为`locked`；
- 标题策略对非Codex Harness执行跳过，未创建官方标题Turn；
- `thread/start`携带Claude transport分类，Host选择`claude-code`；
- 随后的`turn/start`与同一匿名create ordinal匹配；
- 真实Claude SDK子进程由当前Host启动；
- 同轮受控操作还产生了Codex与Pi的匹配路由，未观察到跨Harness误关联。

首次Gate发现Renderer配置注入表达式返回`window`会触发Electron结构化克隆错误。Runner已改为显式返回`null`，并让受控Desktop子进程在`--keep-desktop`下正确脱离Runner生命周期；重试后Renderer Gate进入`ready`。

首次人工Gate发现Question回答后没有Assistant消息，随后第二轮请求虽进入同一个Claude Session也没有可见输出。脱敏协议观察证明Claude SDK和Host已产生完整文本、Item终态和Turn终态；Pi共用Projector也同样不可见。与当前Desktop官方app-server差分后确认，External Thread被错误声明为`source=appServer`、`ephemeral=true`和`historyMode=paginated`，使Desktop选择了错误的timeline路径。

修复后Host使用Desktop客户端分类`source=vscode`，并反映`thread/start`请求的`ephemeral/historyMode`。真实Desktop自动Gate随后证明：

1. Claude普通文本在当前可见Thread显示；
2. 原生Question显示并接受回答；
3. 回答后的Claude文本在同一Turn显示；
4. 紧接着的第二轮Claude文本在同一Thread显示；
5. 不再出现无后续输出的“继续”占位；
6. 点击Desktop停止后产生唯一`interrupted`终态，Thread恢复idle并可继续显示下一轮文本。

差分矩阵分别验证了`source`、`ephemeral`和`historyMode`的部分组合，只有与官方Desktop对话Thread一致的组合通过。中间尝试的用户消息Item投影未改变浏览器结果，已移除，不进入最终实现。OpenSpec任务6.3据此完成。
