# Design

## Context

DSH Web（`packages/bundle/web-app`）同时装配四个右侧栏插件和对应后端：文件读取、终端控制、Office 转 PDF，以及本地文件系统和子进程/PTY 实现。codexhost 已引入其中的插件外壳、文件读取与终端控制源码、Office 转换队列和 DSH 网关源码；缺少的是装配，以及 DSH 本地文件系统、子进程和沙箱策略三个依赖包。

当前 `packages/web-server` 自己实现 DSH 前端调用的接口，没有处理文件和终端请求的代码，因此插件不能只在前端开启。

## Decisions

### 1. 在 Web 服务进程内运行 DSH 后端

在 web-server 内创建一个插件运行上下文（cordis，仓库已在使用），装载 DSH 的文件读取、终端控制、Office 转换服务及其本地依赖。web-server 把这些服务所属命名空间的请求交给 DSH 网关处理，二进制分段与流式推送沿用 DSH 网关原有实现。不在 Host Runtime 或共享契约中新增接口，不新增传输协议。

### 2. 只写最小对接层

- **会话→工作目录**：替代 DSH 的会话服务，按 Thread 标识从 web-server 已有的会话数据取得本地工作目录；取不到时返回未找到，由 DSH 代码按原有路径报告不可用。
- **沙箱策略**：只提供上游服务读取的工作区根目录。
- **终端所属会话**：DSH 终端控制以 DSH Agent 为参数，只用到其标识、工作目录、子进程能力与生命周期。以最小适配对象或最小上游补丁提供这四项，不引入 DSH Agent 运行体系。

上游源码的修改仅限上述对接点，并在导入记录中逐项列出。

### 3. 终端沿用 DSH 的 Node PTY 实现

沿用 DSH 子进程包的 PTY 实现，不在 Rust 层另写。这偏离了 AGENTS.md「进程管理归 Rust」的规则，理由是：这是对上游代码的原样复用，且 `host-runtime` 已有在 Node 中启动子进程的先例。终端进程随 Web 服务进程退出而清理，与 DSH Web 一致。

## Risks / Trade-offs

- [DSH 网关无法直接在 web-server 中运行] → 任务 1 先用文件树做最小验证；若不可行，再只为这几个命名空间写转发，仍复用 DSH 服务本身。
- [终端原生依赖与 Office 引擎增加打包体积和平台适配工作] → 在发行目录验收；某平台无法打包时在文档中注明该平台不支持对应能力，不改写实现。
- [文件预览和终端以系统用户权限运行] → 与 DSH Web 一致，只依赖现有 Web 登录认证；在 `standalone-web.md` 中说明。
