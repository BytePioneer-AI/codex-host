# 验证结论

验证日期：2026-08-22

## 本轮故障与修复

Mac 同时运行本地 codexhost Desktop 与托管 SSH Host 时，非交互 shell 的远端启动块会把 `CODEXHOST_HOST_RUNTIME_PATH`、`CODEXHOST_DATA_DIR` 等变量重新注入本地 Desktop 的 Codex Shim。由此依次出现两类启动失败：

1. 本地 npm Launcher 的更新元数据与远端复制的 Host Runtime 混用，触发 `npm platform package root does not own the Host Runtime`。
2. 本地 Host Runtime 继承远端 `CODEXHOST_DATA_DIR`，与远端 listener 争用同一个 Mapping Store，触发 `Another codexhost process owns Mapping Store`。

修复在三个启动边界上保持同一约束：npm 入口只在检测到托管远端 shell 环境时移除远端启动变量并恢复本地数据目录；native Launcher 显式把本地数据目录传给 Desktop；Shim 在存在本地 Launcher 身份时优先选择本地 npm Node 与 Host Runtime，并清除远端数据目录。直接由 SSH 启动、没有本地 Launcher 身份的 listener 继续使用远端 runtime 与 `~/.codexhost/remote/data`。Host Runtime 的更新协调器还会校验实际 runtime 是否归属于 npm package root，路径不匹配时不启动 npm 更新流程。

## 旧外部任务恢复补充验证

后续实机验收发现，一个在热修期间创建的 Claude Code 任务可以正常对话，但 Desktop 冷启动后恢复该任务时报 `cursor anchor is no longer present`。Mapping Store 当前文件与前一 revision 备份对比证明既有 Turn 映射没有被清空或改写；Renderer 请求跟踪进一步定位到 Desktop 会把 `thread/resume` 返回的全局 `itemsBackwardsCursor` 依次用于多个带 `turnId` 的 `thread/items/list` 请求。

CodexHost 原实现先按 `turnId` 过滤 Item，再在过滤后的集合中解析 cursor anchor，使属于另一个 Turn、但仍存在于同一 Thread 的合法全局 anchor 被误判为丢失。修复把处理顺序调整为：先在完整 Thread Item 序列中解析全局 cursor 边界，再应用 `turnId` 过滤；真正不在全局历史中的 stale cursor 仍返回参数错误。
