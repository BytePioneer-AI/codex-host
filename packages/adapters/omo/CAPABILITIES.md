## 受限与已知缺口

- **派生会留下一个中间 startup 副本会话文件**：每次成功的 Fork / rollbackLastTurn 都会先以 `--fork <source>` 启动一个完整副本（新会话 id），再派生目标会话。5.1.83 不自动回收该中间副本；它是目标会话 `parentSession` 指向的原生父会话，删除会让派生链悬空，因此成功路径保留（一次派生多一个原生会话文件）。失败路径由适配器删除本次创建的两个文件（不碰源文件）。
- **1-turn rollback 的 blank 会话由适配器写入文件**：5.1.83 对 `fork(root user entry)` 得到的内存空白会话不写文件（配置写、close、clone 均不落盘；task-12 blank probe 证明）。适配器按会话格式写 header（同引擎 mint 的 id、`parentSession` = startup 副本）并以 `--session` 重开，引擎在 resume 时追加自己的 setup entries；这是 Pi 适配器 `persistEmptyPiSession` 的同款恢复。适配器不 invent 会话 id。
- **Fork 的 tip 分支不用 `clone`**：`--fork` startup 副本本身即 clone 语义（与 `pi-adapter.ts` 的 fork 分支一致），少一次会话复制；派生 id 仍与源不同。
- **fork 可被扩展取消**：引擎 `fork` 响应的 `cancelled:true` 映射为 typed `nativeFailure`，startup 副本被删除，不静默保留副本。
- **steer（插话；模板无独立行；结论：支持，动态声明）**：原生 `steer`（`docs/rpc.md:4722`，`expectedTurnId`/`turn_conflict` 守卫）已由计划任务 11 的真机 gate 证实可用——隔离 agent dir、真实 omo 5.1.83、Windows：回合首个动作是 `powershell Start-Sleep 15`（eval 内 shell）工具调用；工具执行期间 `capabilities.steer === true`，适配器发 `steer {message, expectedTurnId:"1", clientTurnId}`，引擎原始回帧 `success:true, data.disposition:"queued"`（wire 逐字：`expectedTurnId` 取自 prompt 响应 `data.turnId:"1"`；`queue_update.steering` 随即出现该文本）。工具结束 → `turn_end` → 同 `clientTurnId` 的 `turn_start` 续跑 → `STEER-OK` 文本 → 唯一 `agent_settled`；结算读历史恰 2 条 user entry（prompt `f5b866f8` + steer `8bdffca6`），Turn 身份/checkpoint 仍是 `f5b866f8`，`readSnapshot` 两 Turn 与计数一致（第二条 input 为 steer 文本、agent 文本 `STEER-OK`）；工具结束后 `capabilities.steer` 立即回到 false。实现：`src/omo-steer.ts`（窗口跟踪、准入分类、结算计数对账）+ `src/omo-session.ts` 接线（动态 getter、`turn.steer`、`pendingSteers` 结算等待、target-ended/计数失败后的 fault）；单测 `test/omo-steer.test.ts`（窗口开闭、`turn_conflict`、终结后回执、交付不确定抛错、计数对账）。**受限**：(a) 只在原生 root 工具执行期间声明；文本流、空闲、终态、取消期间不声明（Host 走停止后重发）；(b) 该 gate 只覆盖 1 个回合 / 2 次 provider 请求与 `newapi/deepseek-v4.1-flash`（引擎自带扩展在启动时把隔离 settings 的 glm-5.3-flash 改成 deepseek-v4.1-flash，`persistDefault:false`）、Windows + classic；其他 Model/Provider/OS 不能由此推定；(c) 超时、断链、`disposition:"handled"` 等投递结果不确定一律抛错（Host 记为未知、不自动重发）；终结后回执照 `SteerTargetEnded` 保留历史、关进程并 fault；接受却未落 user entry（计数不符）会判 Turn 失败并 fault 进程，防止残留队列污染下一轮；(d) inspect 的静态能力表仍是 `steer:false`——它没有活动 Turn，live 能力只能由 Session getter 提供（同 omp 的 inspect 不声明 steer）。详见 `.omo/evidence/task-11-add-omo-harness.md`。
- **A8 classic 模式双开残余风险**：classic 模式不执行 `session_held` 守卫（`docs/rpc.md:4364`，仅 daemon 族 host 执行）。用户自己的 OmO TUI 正打开同一会话文件时，codexhost 的 classic resume 可能同时写入；适配器不做 `session-holders` 目录硬拒（会用 stale holder 卡死崩溃恢复），只在文档与本清单记录风险。

- **T9 实测发现：lsp-daemon 残留**：引擎懒加载的 lsp-daemon（`binary-runtime/<v>/plugin/runtime/lsp-daemon`）是脱离父进程树的守护进程，适配器 close 的 `taskkill /t /f` 杀不到它（实测 PID 双回执中该进程 ESRCH 为 false）。属引擎守护进程语义；对 IS-4「不留 omo 进程」的严格口径需在 T5/T17 决策（记录 vs 追杀）。
