# Web Server

A separate Node server for the responsive DSH-derived UI. By default it starts or connects to one independent local CodexHost service: canonical Threads, history and mutations remain owned by CH, whether or not Desktop is open. It neither starts/stops Desktop nor opens a second external Adapter or Mapping Store. External rendering buffers are in memory; existing Web workspace records group CH Threads by their actual GUI project membership, not execution cwd alone. Unselected/generated directories stay out of the project list; assigned worktrees share their parent project while retaining their real cwd. Native project metadata is read-only, with no mkdir or GUI project creation. `--session-source standalone` explicitly selects an independent composition using the same isolated session implementation.

Build from the repository root with `npm run build:web`. The default plugin input is the same checkout's `packages/host-runtime/dist/plugins`, built by the existing CH release plugin builder; the installed CodexHost.app is not consulted. Usage-only plugins are excluded from conversations. The standalone Codex Adapter lives in `packages/adapters/codex`; no Harness implementation is duplicated here.

`npm start web` builds and starts the environment-isolated, authenticated preview without running Desktop cleanup. Successful builds show only progress and elapsed time; failures show up to the last 64,000 characters of diagnostics and prevent launch. Run `npm run build:web` for full output, or use `npm start web -- --no-build` to reuse artifacts. It listens on `0.0.0.0:4400` by default for LAN/Tailscale access; authentication and same-origin checks remain enabled. Startup output left-aligns token-bearing URLs and a labeled phone QR code, without printing the data directory or Harness catalogs. Interactive builds update the actual phase, completed frontend-plugin count and elapsed time on one line, with a blank line before access URLs. Use `npm start web -- --host 127.0.0.1` for loopback-only access. Firewall/network reachability is still required; use a trusted network, Tailscale, or HTTPS rather than exposing plain HTTP to the public Internet. `npm start` without `web` still launches Desktop, and `npm run start:web` remains a compatible alias. Either Web or Desktop can start/connect to the same background owner; closing either UI does not stop the other or its running tasks. The native Launcher owns detachment, concurrent-start admission and old-process-tree cleanup, while the service owns the sole writable store and Harness registry. The current-platform packed distribution includes this Launcher and the same Host bundle, not Node or Harness CLIs. Updated local Hosts provide an authenticated event channel in `~/.codexhost/client-hosts`; use `-- --ch-data <host-data>` for another owner data directory, separate from Web's `--data`. Optional paths are `--ch-launcher`, `--ch-host-runtime`, `--ch-plugins` and `--ch-codex-home`. Projects come from read-only native persisted metadata without Desktop; pin writes still require Desktop's native service. An old Desktop-owned endpoint may be used but is never taken over or killed: transition requires a user-arranged Desktop update/restart. Supplying only `-- --ch-cdp http://127.0.0.1:<port>` explicitly selects the legacy path; combine it with a control directory for events and GUI-dependent pin access. Building Web does not replace a running Host. Neither disconnect nor recovery falls back to standalone or resends uncertain mutations. `npm start web` enables every bundled session Harness, including Codex and Pi, by default; only `-- --port <port>` is needed to change the listener. The launcher supplies the Codex CLI path using native installation inspection or PATH. A failed Codex connection is logged without blocking Web startup; explicit migration failures still stop startup. Selection does not install/authenticate CLIs or change Adapter, model catalog or session behavior. Advanced `--harness <id,...>` and CLI/home overrides remain available. For independent plugin mode use `-- --session-source standalone`, which still defaults to Claude Code; standalone Codex still requires selecting it alone. Explicitly selecting missing or usage-only plugins remains an error. The packed entry is `dist/codexhost-web/preview.mjs`; it strips inherited Desktop routing and Node injection variables, preserves CLI credentials/PATH, and stores preview data separately. `server.mjs` is the configurable full entry and must not be launched with inherited Desktop routing state.

Web-owned data defaults to `~/.codexhost/web/` for both the direct server and preview. Custom `--ch-data <root>` defaults Web storage to `<root>/web`; explicit `--data` remains independent. This consolidates configuration, authentication, Push state and attachments without changing the Host's sole session ownership or moving user projects/native Harness homes. Legacy profiles are never merged automatically: if the default destination is absent but old default directories exist, startup requires offline migration or an explicit `--data`. Recorded offline root moves can retain compatibility links for historical attachment paths; migrated owned images still require content-hash validation, and arbitrary symlink reads remain prohibited. See the [data directory constraints](../../docs/product/standalone-web.md#web-数据目录).

The root `test:shared-host` script tests real Launcher/Node lifecycle with isolated homes and fake native protocols. Node test-runner suites are owned by this package's `test`, `test:distribution` and `test:browser` scripts; the root TypeScript test command invokes the unit suites separately from Vitest. The backend suite includes real HTTP entry-point tests; its `pretest` builds frontend artifacts so a clean checkout has the same startup prerequisites as the real server. Browser and distribution suites also require built frontend artifacts. They use temporary data, fake Harnesses and a fake CH/CDP peer, never real model submissions. The generic authenticated App gateway is `/api/ch/v1/{events,rpc,snapshot,respond}`. It uses the same Host owner and never exposes its private discovery token. See [the client protocol](../../docs/architecture/host-client-channel.md) for invalidation/snapshot recovery, arbitration and bounded receipts. Event-mode Web shares approvals/questions; legacy CDP mode still handles them in GUI. Project metadata retains periodic checks; generic file preview/download, shared Web Steering and complete background/subagent projections remain limited.

Local shared mode accepts PNG/JPEG/WebP/GIF clipboard, picker and drop images. Sending saves exact uploaded bytes under `<data>/attachments/images` and passes native Desktop-style attachment path context to the Host; it does not change the Harness input protocol or Codex configuration. Authenticated previews are reconstructed from the native Thread's own path references, including Desktop clipboard/original images and structured local/inline image input. Presentation separates the user's request from execution context and shows ordinary native files as read-only reference cards. Image reads require both the current Thread's loaded canonical input and its display reference; guessed IDs or browser-supplied paths cannot authorize reads. Native bytes stay at their original paths, HTTP/remote image URLs are not fetched, and unavailable images remain placeholders beside the user's request. Limits: 20 MiB/image, 20 images/32 MiB per message, 8192 pixels per side, 64 million pixels; HTTP RPC bodies are capped at 48 MiB. Files are retained after ambiguous submissions and across restarts. The Harness must be able to read the same local filesystem; remote/WSL path translation and standalone attachments are not enabled. `image-size` performs header checks and its MIT notice is included in packaged licenses.

Local shared mode also streams arbitrary file types through the existing background upload UI and authenticated `/api/session/uploadFileBinary` route. Exact bytes are saved under `<data>/attachments/files/<sha256>/<safe filename>` and only Session-scoped opaque receipts are accepted by prompts; selecting files never allocates a native Thread. Local ordinary files have no application-level size, count, total-byte or pending-receipt count quotas. Browser Blob/Uint8Array/stream carriers all use raw-byte intake rather than bounded JSON RPC; storage remains streamed. System/filesystem/network constraints still apply, and image limits remain separate. Pending receipts expire after one hour or a Web restart; accepted receipts retire, while refused/ambiguous sends retain their bytes. Native history restores file cards without a second Thread index. No auto-execution, archive extraction, universal preview or file download endpoint is added.

The initial Web implementation is imported from the MIT-licensed `codexhost-web` fork; its upstream license is retained in `LICENSE.upstream`. Current behavior, limitations and ownership are documented in [standalone-web.md](../../docs/product/standalone-web.md).

Default Codex enablement configures one isolated source owned by the shared background service alongside external Threads. Its canonical native home still defaults to `<web-data>/codex-home` (`--codex-home`), while shared metadata/journals and local workspace/pin/archive records live under `<ch-data>/web-codex`. Configure and authenticate the CLI in that isolated home; GUI credentials/history are never copied or taken over. Web is a viewer/gateway and may stop while the owner continues; Push still requires the gateway. Profile/home locks prohibit concurrent shared/standalone writers, and an unconfirmed native close blocks ownership release. Crash recovery requires the Rust supervisor's private exit proof matching the previous PID, generation and canonical owner root; absent/mismatched proof refuses recovery. These locks do not protect against a user manually running another CLI in that home. Owner-level bounded Session/requestId receipts deduplicate identical input across gateways and reject conflicting input; they do not promise exactly-once after eviction or restart.

`--session-source standalone --harness codex` uses the same session-runtime implementation with an independent composition/root and closes its own native sessions on shutdown. Shared mode never falls back to standalone. Existing local data is migrated only with `--web-codex-migrate-source <old-web-data> --web-codex-legacy-stopped` and an explicit unchanged `--codex-home`; confirm the old service is idle with no queued or unresolved work before normally stopping it. Invalid schema/journal or identity/target conflicts stop migration without changing the source. Commit seals the old source against updated standalone writers; older lock-unaware binaries must stay stopped. Keep the old home and attachment paths; there is no automatic attachment move, ID alias or rollback after new writes. Offline maintenance uses the Host entry's `--codexhost-web-codex-rollback --data <host-data> --home <original-home> --launcher <launcher>`: native stop and exit/lock confirmation precede rollback, which unseals the source and retires the target configuration. The [Web Codex section](../../docs/product/standalone-web.md#web-codex-加载隔离与路由) describes the steps and limitations. Codex requires an explicit workspace and text input; native capabilities are unchanged, and official GUI Threads remain outside this source.
